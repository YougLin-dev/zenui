# ZenUI 愿景

ZenUI 让 Rust 开发者以熟悉、简洁、类型安全的方式，构建具有原生平台体验、细粒度更新和明确生命周期的桌面应用。

这三项构成一个整体：界面表达不能以浏览器运行时和虚拟 DOM 为代价，平台能力不能以冗余的状态同步为代价，运行效率不能以模糊的资源与生命周期为代价。

## 起点

ZenUI 首先服务于使用 Rust 构建本地工具的独立开发者与小型开发团队，例如开发工具、笔记、清单、数据查看器和内部系统。

这些应用需要完整的桌面能力：文本输入与输入法、焦点、列表、多窗口、主题、菜单、对话框和后台任务。它们不需要为了界面而引入第二套语言、前端工程和浏览器运行时。

ZenUI 首先建立一套可靠的开发模型与扩展边界，而不是以组件数量代替框架的完整性。

## 三项原则

### 熟悉的表达

普通 Rust 负责逻辑，`view!` 描述结构。组件、属性与回调具有 Rust 类型，保留 Rust 的控制流与错误处理。

Tailwind 风格的 class 以简洁的词汇描述常用布局、颜色、间距、排版与状态样式，在编译时转换为原生声明；动态样式使用类型化输入。

这种表达方式借鉴熟悉的界面词汇，不实现浏览器 DOM、通用 CSS 引擎或运行时 CSS 字符串解释器。

### 原生体验

ZenUI 直接使用操作系统的窗口、输入、输入法、菜单、对话框与辅助功能。

界面节点由框架保留并绘制，连接原生平台服务。这里的原生不以每个控件都由操作系统提供为前提。

跨平台能力以实际行为为边界。文本输入、IME、焦点、DPI、窗口与辅助技术需要在对应平台上验证，不能以同一套代码可以编译代替。

### 稳定的身份与生命周期

组件只挂载一次；字段变化更新相关节点和绑定，不重新执行整个组件。

界面树保留节点身份与本地状态。列表按业务键重排，保留焦点、光标和选择；结构变化挂载或卸载分支，并管理其订阅、回调和资源。

Copy handle 简化状态与平台对象的传递，但不复制数据或延长生命周期。业务模型、界面状态、宿主服务与渲染资源各有明确归属：控件卸载不删除业务数据，旧异步结果不写入新一代界面。

细粒度限定相关工作的范围，不承诺无条件的常数时间开销。文本与布局变化需要的计算仍是实际工作的一部分。

## 克制的能力边界

ZenUI 不追求以下方向：

- 嵌入式 Web、JavaScript 运行时或现有 Web 应用的自动迁移；
- 面向 Web、移动端、SSR 或 hydration 的多目标框架；
- VDOM、组件反复重建或并行的第二套界面更新机制；
- 完整的浏览器 CSS、任意选择器与运行时样式插件；
- 游戏引擎、通用 ECS 或捆绑的异步运行时；
- 依赖未经验证的能力宣称完整的桌面或跨平台支持。

ZenUI 以二维桌面界面为主干。图像、视频、外部纹理和三维场景可作为布局中的内容节点接入；完整三维资产管线与引擎功能不属于核心 UI 模型的前置条件。

## 首个完整目标

以一个真正可交互的桌面 Todo 验证整套开发模型：文本输入与中文 IME、增删改、筛选、列表重排、键盘与焦点、状态样式、深色主题、窗口关闭和文件导入组成完整工作流。

它需要同时证明熟悉的语法、正确的更新与生命周期，以及平台与渲染能力的连通。开发者能够不依赖隐含约定，理解、运行和复现这个应用。

在此之前，headless 测试、宏转换与图形原型仅证明相应局部机制。
