# 实验方案

## 正在验证的核心假设

目标语法希望同时做到：

- Copy handle 可以在多层 `move` closure 中直接携带；
- `Signal<String>` 不要求 String 自身 Copy；
- 数据位传 handle 就能持续更新，`once` 明确一次性输入；
- 普通 UI handler 中的 `.set(v)` 直接完成，不产生逐次 `Result` 样板；
- 模型事务与 UI reset 保持各自职责；
- 多窗口、异步 job、renderer 都拥有清晰的代际生命周期。

当前优先探索的是 **Copy identity 与 framework 安装的执行上下文**。运行时负责检查来源、owner、phase 和 registration；安全 identity 不依赖 `Rc`、全局单例 registry 或公开裸指针。

类型形状可以被直接验证，但这不足以证明整套 update / lifecycle 语义。完成以下实验之前，目标 SDK 的相应行为保持开放。

## 还要确定的语义

### 普通读取和非法调用

简单 `get()` / `set()` 的简洁写法与错误上下文的拒绝存在边界。写入非法 phase 时，不能让用户代码正常继续再假定一次事后错误日志可以解决副作用。

实验需要给出：错误 phase、离开运行上下文、已销毁 owner 三种情况下的停止位置，frame 怎么被放弃，下一合法 command 又如何干净恢复。

### Field 的失效调度

理想的正常删除不会先让 field binding 读到一次 MissingRow。它先由行集驱动对应消费者退出，再处理该 epoch 中其他字段的更新。

需要验证：字段的普通失效不会使已删除的行重新出现，正常 Delete 也不会误报为异常读取。Field failure 的 patch 策略不能默认所有失败都回滚无关模型事务。

### Command 与异步结果职责

`WriteOp` 的构造是否完全惰性、handler 尾值何时被消费、事务 root 如何界定、task scope 与 window anchor 的区别，都需要由结果 trace 固定。

错误报告只能观察这些事实，不能接管 commit / cancel / persistence decision。

### 行列身份与资源

`once` 基于 mount 而不是 row pool，Copy content 不等于 GPU attachment。列表的 owner、控件编辑状态、renderer lease、device generation 分别需要局部验证。

## 第一阶段：headless authority

不引入 proc macro 和 GPU，先验证基础状态机。

用目标形状构造深层 `move` closure，保证没有显式 clone。覆盖：

- 两个 Store / Runtime 不串读；
- event read 与 Memo tracked read 的区分；
- dynamic dependency replacement；
- write in compute 和 write inside `with`；
- owner dispose、slot 复用、同名业务 key、代际耗尽；
- 一行被移除时，当前订阅先停止；其他行的字段更新不受影响；
- 一个 app Memo 被两个窗口消费，关闭其中一个后另一个仍更新。

每次断言都包括值、通知、依赖、调用次数与后续可恢复 command，而不仅是当前界面是否最终一致。

## 第二阶段：命令与异步桥

建立最小的惰性命名单元与确定性任务队列：

```text
event -> inert WriteOp -> 模型事务 -> UI reset -> 统一 publication
                    -> 唯一错误或取消出口
```

worker 只取得 Send job，返回 PreparedImport 或失败。窗口关闭与重开、旧 scope 的完成、模型 commit 与 UI delivery 的分离都模拟独立结果的到达顺序。

场景至少覆盖：

1. 构造 op 但不提交，模型不发生任何变化。
2. handler 返回 op，恰好执行一次，不会重复派发。
3. 同步 Add 模型提交与 draft reset 产生一次一致 publication。
4. 模型拒绝时 draft 保留，后续干净 command 仍有效。
5. worker 在 Main 旧 activation 结束后完成，旧 delivery 不可投递新 Main。
6. AppTasks 的 job 可以跨窗口继续，但不复用旧 renderer attachment。
7. 用户已输入更新的 draft 后，旧 completion 不清空它。

## 第三阶段：宏与 typed adapter

在底层语义稳定之后再实现目标 DSL。

- 每种 property 接受明确的 source 类型，不发明通用任意 `IntoBinding`。
- `Show.fallback`、`For.row`、`VirtualList.key/item/a11y_item` 与 Children 各自有严格回调形状。
- 组件是 deferred mount，`?` 保持普通 Rust 控制流，失败只取消拟议 mount。
- 调错类型时定位到具体 property / argument，不把整段 `view!` 报错作为唯一诊断。
- 检查 `WriteOp` 与 Result 尾值，既不吞错，也不意外隐式执行。
- 两个 `move` 分支中的共享 resource handle 使用明确 content role。

## 第四阶段：宿主与原生验证

先使用可手动排序的 fake host：

1. 声明错误不发布目录，也不调用任何 window factory。
2. `show/show/hide/show/close/show` 的 factory 次数是 `1,1,1,1,2`。
3. 旧 native event 不影响新 generation。
4. 重复关闭、Deny、确认窗 X、旧 reply、Allow 都产生可追踪的局部结果。
5. app job 与 window job 的取消与交付独立。

之后再走过真实平台的 native boundary：输入、IME、读屏、模态阻断、Dock reopen、DPI、surface / GPU teardown。只有这些实际场景通过后，才可把目标 SDK 对应的能力归为可用。
