# 性能与内存门禁

本页说明可执行的性能/内存门禁，以及如何阅读 `bench/baselines/*.json`。门禁实现在工作区成员 `crates/perf`（二进制 `zenui-perf`），不复用测试专用代码。

## 运行

```powershell
# 列出固定负载
cargo run -p zenui-perf --release -- list

# 只测量并打印；不写文件
cargo run -p zenui-perf --release -- run --bench toggle_row_10k

# 比较基线；计数在所有机器上强制，时间只在同一 runner/指纹上强制
cargo run -p zenui-perf --release -- check --runner perf-windows --require-time

# 在固定 runner 上录制基线（会更新 bench/baselines/<bench>.json）
cargo run -p zenui-perf --release -- record --runner perf-windows
```

`check` 需要 release 构建；debug 构建直接拒绝。`--bench` 指定单个负载，缺省运行全部负载。`--baseline-dir` 可指向临时目录，用于验证门禁本身。

## 固定负载

| bench | 场景 | 关键计数上限 |
|---|---|---|
| `intent_noop` | 10k 行窗口化列表上的空 handler + 空事务 | 快照根 0、重建节点 0、场景构建 0、绑定求值 0、memo 重算 0、分配 ≤192 |
| `signal_equal_write` | 10k 行直接绑定同一 `Signal<String>` 后的相等写入 | 绑定求值 ≤1、memo 重算 0、快照根 0、场景构建 0 |
| `toggle_row_10k` | 32 行窗口内切换第一行完成状态 | 绑定求值 ≤8、重建节点 ≤32、场景构建 1、挂载节点不增长 |
| `typing_10k` | 窗口化 10k 行旁的编辑器每 turn 插入一个字符 | 重建节点 ≤4、绑定求值 ≤4、场景构建 1、场景元素 ≤128 |
| `scroll_10k_within_row` | 20px 行内 5px 偏移变化 | runtime turn 0、快照根 0、重建节点 0、场景构建 1 |
| `scroll_10k_cross_row` | 跨一行移动行窗口 | changed turn ≤1、快照根 1、重建节点 ≤32、场景构建 ≤2 |
| `theme_switch` | 三窗口切换应用外观 | 三窗口 revision 前进、快照根 3、重建节点 0、场景构建 3 |
| `multi_window_3` | 三窗口共享状态，只有窗口 a 读取被改信号 | 前进窗口 1、未变化窗口 2、未变化窗口快照/场景构建 0 |
| `memory_soak` | 10k 行窗口移动 + 行增删 + 过滤切换 10 轮 | 共享投影单独计费；storage 增长不超过页粒度；挂载节点 O(窗口) |

计数名称与语义：

- `snapshot_roots_built`：本 turn 实际构建的快照根数量；revision 未变时的读取复用 `Arc`，不计数。
- `snapshot_nodes_rebuilt`：`PresentationDelta` 的 changed + inserted 节点数。当前实现每个新 revision 仍重建整个可见根；该计数衡量发布给 renderer 的增量范围，不表示跨 revision 的结构共享。
- `bindings_evaluated` / `memo_recomputed`：动态绑定槽求值次数与生产 memo compute 次数，按 turn 读取差值。静态/once 槽不计入。
- `scene_builds` / `scene_elements`：本 turn 是否重建场景以及场景元素数；场景是完整 Taffy 重排，不声称增量布局。
- `allocations`：进程级计数分配器（`GlobalAlloc` 包装）在计时 turn 内的分配与重分配次数。
- `mounted_nodes_growth`：本 turn 前后 live 节点数之差；窗口化行变化不应增长。
- `storage_memo_deps_live` / `storage_memo_deps_storage` / `storage_memo_storage_bytes` / `storage_memo_deps_storage_bytes`：已挂载 memo 的依赖条目数、依赖列表容量、memo 槽容量字节与依赖容量字节；与 `memo_slots`、`dep_entries`、`consumer_edges` 一起确认反向图不随 churn 历史增长。
- `storage_signal_slots` / `storage_memo_slots` / `storage_free_signal_slots` / `storage_free_memo_slots`：Signal/Memo 槽数组长度与 free list 长度；复用后槽数组不随挂载历史增长。
- `storage_binding_consumer_edges` / `storage_binding_consumer_nodes`：绑定与结构触发的消费者边、已登记节点数；卸载后必须随挂载节点回落。
- `storage_field_write_entries` / `storage_write_epoch_entries`：字段写入尝试与失效代数条目；删除行后对应条目被清除，不随交互历史增长。
- `storage_owner_records`：owner 记录数；普通元素不单独创建 owner，只有组件、Show、For、窗口与应用级 scope 计入。
- `signal_memo_bytes` / `owner_bytes`：`MemoryReport` 中的 Signal/Memo 槽、值估算与依赖容量，以及 owner 记录与登记表容量。值的堆字节是诊断估算：`String` 按容量、其他类型按 inline 大小，共享 `RowSet` 缓冲只在 `rowset_bytes` 计一次。
- `memory_soak` 的 `storage_growth_*`：预热高水位之后的 arena 容量增长，包含 `memo_deps_live` 与 `memo_deps_storage`；`rowset_bytes`、`rowset_shared_count`、`rowset_count` 分别报告共享投影字节与句柄数。`rowset_bytes` 按每行 8 B 计费，重复投影各计一份。

## 基线与噪声

`bench/baselines/<bench>.json` 记录：

- `runner` 与 `fingerprint`：OS、架构、CPU 标识、逻辑核数、`rustc --version`、profile、字体来源；
- `git`、`recorded_unix_seconds`、`noise { warn, fail }`；
- `limits`：硬上限，`check` 只读取这里；
- `measured`：录制时的实际计数，只用于趋势；
- `timing_ns`：`min`、`fast`（最快十分位均值）、`median`、`p50`、`p95`、样本数与每个样本的连续 turn 数；
- `clock_ns`：录制时固定算术负载的最快值，用于归一化机器频率差异。

计数上限在任何机器上都检查，超过 `limits` 即失败。时间门禁在以下条件同时满足时启用：当前 runner 标签等于基线 `runner`，`fingerprint` 完全一致，且当前 fingerprint 的 profile 为 release。时间比较使用 `fast_ns / clock_ns` 归一化后的比例：超过基线 10% 警告，超过 15% 失败。样本把多个连续 turn 合成固定长度块（例如 128 次空 click），`min`/`fast` 对真实回归仍敏感，但对单次调度抖动不敏感。

`dev*` runner 是本机临时基线：时间默认只报告趋势；`--require-time` 才阻塞。固定 runner（例如 `perf-windows`）必须用自己的标签重录基线，否则 `--require-time` 会失败并要求重录。时间超限会整条负载重测一次；两次都超过 15% 才失败。计数失败从不重试。

## CI

`.github/workflows/perf.yml` 定义：

- `perf`：每晚 02:00 UTC、手动触发与带 `release` 标签的 PR；运行 `check --runner perf-windows --require-time`。
- `soak`：每周一 03:00 UTC、手动触发与 release PR；只运行 `memory_soak`。

job 使用 `[self-hosted, windows, perf-windows]`。该 runner 需要在仓库外登记并保持安静、固定电源策略；未登记时 job 排队，且不是普通 PR 的 required check。登记后用 `record --runner perf-windows` 更新基线并提交；在此之前仓库内 `dev` 基线只作趋势参考。

## 当前证据与边界

- 门禁本身：`cargo test -p zenui-perf` 覆盖时间/计数比较、噪声阈值、runner 指纹不匹配与开发 runner 的报告模式；`check` 在本地 `dev` 基线通过，计数回归与 +20% 时间回归会在临时基线上分别失败。
- 内存：`tests/memory.rs` 固定 1k/10k 行挂载节点与共享投影的分离计费、两窗口共享同一投影、churn 后 storage 不按历史增长，并验证 Show 反复重挂时 Signal/Memo 槽位复用、值字节回落与消费者边有界；`memory_soak` 在 10k 行、10 轮 churn 上重复同一组不变量。
- 绑定：`tests/binding_metrics.rs` 固定空 turn 不求值、相等写入跳过直接绑定、单行变化只求值该行；差分 oracle 的随机序列覆盖跳过路径后的可见状态。
- 未完成：固定 `perf-windows` runner 与对应基线的实际录制；快照根跨 revision 的结构共享、场景增量布局（[事件与响应式更新-方案](事件与响应式更新-方案.md) §19.10）与 §19.7 的 `MemoCell` 48 B/`SnapshotNode` 头预算仍是后续性能工作。门禁不把当前全量重建或内联 memo deps 表述为增量实现，也不以开发机数字作发布承诺。
