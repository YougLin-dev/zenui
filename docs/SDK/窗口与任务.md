# 窗口与任务

本页描述 SDK 的平台服务边界和窗口生命周期。窗口目录、多窗口 activation、close epoch、关闭确认与原生打开/保存/文件夹对话框已由 runtime 实现；`zenui-windows` 宿主发布只读 UIA 树，实现 Invoke、Toggle、Value pattern、fragment `SetFocus` 方法、最小 `TextPattern` 与窗口根 `ScrollPattern`，并按发布差异投递焦点、属性与结构事件。原生菜单栏由同一宿主从目录声明构建并派发菜单命令（契约见 [ADR-0013](../adr/0013-menu-and-tray-host-services.md)）；每次打开菜单时，应用登记的只读回调提供各命令的 enabled/checked 状态。菜单命令可以声明快捷键，宿主为每个窗口建立 `HACCEL` 并在字符翻译前派发。窗口级上下文菜单同样来自目录声明，由 presenter 在宿主借用之外展示并只派发一次命令。应用托盘由应用级命令承接，宿主为可见模式安装原生通知区域 presenter；隐藏模式用注入的 fake 验收。应用会话在启动前声明最后窗口策略，命令处理器通过 `SessionCtx` 显式恢复窗口或退出。

## 运行时窗口边界（headless 与原生共用）

根包 `zenui` 已经把以下语义做成可运行实现，并用公开行为测试固定：

- `Runtime::setup` 在任何窗口 factory 运行前运行一次应用级 setup，它创建的 Signal、Memo 与 Store 归属应用 Owner，窗口关闭不会释放。setup 失败会释放本次创建的资源并允许重试；成功后再次 setup 或改用 `Runtime::mount` 会被明确拒绝。
- `Runtime::declare_windows` 声明静态窗口目录：`WindowSpec` 提供稳定键、原生标题、初始逻辑尺寸、primary 标记、`ClosePolicy` 与窗口角色，重复键、缺失或多个 primary、无效的确认绑定都是 `CatalogError`；声明不运行 factory、不挂载树。`Runtime::show(key)` 打开未显示的窗口，已显示时只聚焦而不重跑 factory；factory 失败仍消耗这一代 activation，下一次成功打开使用新一代。`Runtime::presentation_of(ctx)` 返回该窗口自己的快照。每个窗口拥有自己的树、焦点、caret/selection 与快照；Signal/Memo/Store 仍共享，模型变化刷新所有窗口。
- `Runtime::hide(ctx)` 保留窗口的 activation、树、焦点、caret/selection 与窗口任务，只停止输入与呈现；`show(key)` 恢复同一 activation 且不重跑 factory。隐藏窗口仍可由 `window_alive` / `window_visible` 观察，但 `presentation_of` 与 Node-ID 派发返回 `Hidden`，不会产生可见快照。
- UI 处理器只持有 Copy 的 `WindowCtx`，因此窗口生命周期动作通过 `WindowCtx::request_show(key)` / `request_hide()` / `request_close()` 排队，再由 `Runtime::apply_window_requests` 在事件或任务交付结束后结算；会话级 show/quit 走 `Runtime::apply_session_requests`，在窗口请求之后结算。headless 驱动在派发后依次调用两者，Windows 宿主自动调用。请求只接受 `Event` / `Delivery` 阶段与存活来源：来源在结算前关闭时被丢弃，`request_show` 的未知目录键在排队时即报错。普通请求结算不派发用户事件；`Confirm` 的 close handler 可以要求显示确认窗口，`request_close` 会在调用它之后立即结算这些 show 请求。返回值是已应用的动作数。
- 关闭协议由运行时拥有：`WindowSpec::close_policy(ClosePolicy::Confirm)` 的窗口在 factory 中通过 `WindowCtx::on_close` 注册处理器；`Runtime::request_close(ctx)` 为每个父窗口创建至多一个待决 close epoch，记录父窗口焦点、挂起其输入，并以一次性 `CloseRequest` 调用处理器。处理器的 `CloseEvent` 返回 `CloseOutcome::{Allow, Deny, Pending}`；从确认窗口回复时用 `CloseRequest::allow()` / `deny()`（例如草稿为空时直接关闭），也可以用 `request_show` 显示目录中以 `confirmation_for(parent)` 声明的确认窗口；`Pending` 保持 epoch 待决并要求同一关闭 turn 内显示确认窗口；确认窗口通过 `WindowCtx::close_request()` 读取请求并回复。Allow 释放父窗口与确认窗口，Deny 释放确认窗口并恢复父窗口输入与焦点；确认窗口的 X、Escape 或关闭请求在待决时表示 Deny。处理器在调用期间直接回复时结果立即生效；从确认窗口按钮排队的回复由 `apply_window_requests` 结算。隐藏的 Confirm 窗口先恢复可见，再建立 epoch，避免不可见的确认提示。
- 从确认窗口发出的 `CloseRequest` 回复先排入队列，由 `Runtime::apply_window_requests` 执行，因此同一 epoch 的第二个回复以及跨 epoch 的旧句柄都返回 `Stale`。重复关闭请求只聚焦确认窗口，不创建新 epoch；隐藏待决父窗口、或其确认窗口关闭，都按 Deny 结算；直接关闭待决父窗口会把确认窗口一并释放。缺失处理器、未声明的确认窗口或处理器未显示确认窗口会返回 `CloseError`，父窗口保持打开，绝不回退为 Allow。
- `Runtime::open_window(key, factory)` 是未声明目录时的单 activation 兼容入口：它只为该 activation 创建树与 Owner，不代表 SDK 的窗口边界。声明目录后使用 `Runtime::declare_windows` 与 `Runtime::show` 管理任意多个目录窗口。每次重开递增 activation，factory 重新执行，旧 activation 的 `WindowCtx` 变为 stale。
- `Runtime::close_window` 释放窗口 UI 和本地资源，取消该 activation 的任务交付，但不销毁共享模型；若该窗口有待决 epoch，先释放确认窗口，再作为一组关闭。
- `WindowCtx::task_scope()` 与 `WindowCtx::app_task_scope()` 区分窗口所有权和应用所有权；app 所有权任务可在窗口关闭后继续提交模型。
- worker 只接收 `Send` job 和结果数据；Copy Signal/Memo/Store Field、`WindowCtx`、`TaskScope` 与 `Task` 都不实现 `Send`，UI-only 值不能跨线程捕获。
- worker 结果由 `Runtime::drive_tasks` 在 `Delivery` command turn 中交给 continuation；旧 activation 的结果在交付前被丢弃，continuation 仍受只读作用域和阶段检查约束。
- `Runtime::settle_tasks` 是 headless 驱动的等待入口；它等待 worker 完成后再交付。真实 UI 事件循环应使用非阻塞的 `drive_tasks`，它轮询已经返回的 worker 结果。
- `Runtime::set_wake_callback` 安装 worker 结果就绪时的唤醒回调。回调在 worker 线程执行，必须线程安全且不能借用运行时状态；运行时不合并唤醒——每个已发送结果且未观察到取消的任务唤醒一次，worker panic 不唤醒。
- stage-one 的任务 scope 只有 app 和窗口 activation 两种；单个组件或 `For` 行还不能拥有任务。这样的 continuation 如果写入已卸载分支的 Signal，会在交付 command turn 中被拒绝，而不是静默写入。
- `WindowCtx::on_keydown` 在窗口 factory 中注册窗口根 keydown fallback，每个 activation 一次。有节点焦点时它按 closest-wins 最后运行；没有焦点时直接运行。处理器可以 `consume` 或 `prevent_default` 阻止控件与宿主默认；关闭窗口释放处理器，重开必须重新注册。

## 平台对象不参与界面描述

窗口、菜单、托盘、系统对话框属于平台服务。它们不进入 `view!`，也不由某个控件隐式创建与原生生命周期无关的窗口。

应用启动时提交静态窗口目录。目录包含稳定键、窗口参数和可重复调用的 factory：

```rust
let state = runtime.setup(TodoState::new)?;
runtime.declare_windows(move |catalog| {
    catalog.window(
        WindowSpec::new("Todo")
            .primary()
            .titled("ZenUI Todo")
            .sized(900, 700),
        move |window| view! { <TodoApp window=window state=state /> },
    )
})?;
runtime.show("Todo")?;
```

这段注册不会打开窗口，也不调用内容 factory。声明失败表示目录未发布；它不意味着可以撤销应用自己执行的随机 I/O 或用户已经看见的宿主副作用。

## 一次打开对应一个 activation

`"Todo"` 是目录中的稳定键，窗口每次真正打开则有独立 activation 和它自己的 Owner。

```text
未打开 -> 打开中(g) -> 可见(g) / 隐藏(g)
                    -> 关闭中(g) -> 未打开
```

这些内部状态带来以下直观行为：

- `primary()` 标记 Host 首次显示的默认入口；自定义 reopen 走同一条 show 路径。
- 打开的窗口再次 `show()`，聚焦或复用现有实例，不会重复 mount 或创建第二份订阅。
- `hide()` 保留 activation 和本地控件状态，但停止输入、语义动作和呈现；若有待决的关闭确认，这次 hide 按 Deny 结束它，隐藏后不再等待后台 reply。
- `close()` 结束 activation；下一次 `show()` 再执行 factory，创建新 Owner 和新一代本地资源。隐藏的窗口要关闭或重新确认时，先恢复可见再走关闭协议。

目录键与 activation generation 各管一件事。原生 WindowId 或许会被平台复用，不能用它单独判断回调属于哪一次打开。

`WindowCtx` 可以作为 Copy bound handle 携带在事件中；让它复制更方便，不等于保持窗口活着。菜单、任务和延迟 reply 都需要经过有效 activation 的分发检查。

## 关闭确认是一次决定

父窗口可能拒绝关闭并要求确认。系统将这个决定绑定到父窗 activation 和一个 close epoch：

- 同一个 epoch 内，连续点击关闭不会创建多个确认窗。
- “继续编辑”意味着 Deny：关闭确认窗、恢复父窗 input / focus，父窗仍是同一个 activation。
- “放弃修改”意味着 Allow：确认窗与父窗作为一组释放。
- 确认窗的 X 或 Escape 默认是 Deny，不能让确认窗消失后父窗还保持模态禁用。
- 第一个有效 reply 生效。后续迟到的 Allow 不会放行另一代关闭请求。

确认窗口通过 `WindowCtx::close_request()` 取得 `CloseRequest`，按钮直接调用 `allow()` / `deny()`。句柄携带父窗口 activation 与 epoch；框架据此拒绝同一 epoch 的第二次回复、跨 epoch 的旧句柄，以及父窗口已由其它路径关闭后的回复，不需要另设一组长生命周期 token。

关闭策略失败或确认窗构造失败，不能让父窗默认进入 Allow；应恢复可操作状态并报告失败。

如果消失的只是窗口 UI，AppState 可以继续存在。未保存业务状态由独立的 discard / restore policy 处理。

## Hide、Close、Quit 不是一件事

隐藏窗口不会结束应用或会话，并保留 activation、树、焦点与本地编辑状态。关闭窗口只释放 activation；共享模型、AppTasks 与应用会话仍由 Runtime 拥有。

应用会话策略在首个窗口打开或根树挂载前声明一次；没有声明时使用 `QuitOnLastClose`：

```rust
runtime.declare_session(SessionPolicy::StayResident)?;
let session = runtime.session();
runtime.on_app_command("app.quit", move |_| {
    session.request_quit().expect("queue the quit");
})?;
```

- `SessionPolicy::QuitOnLastClose`：默认策略，最后一个窗口关闭后原生宿主结束消息循环；Runtime 模型仍保留，嵌入方可以重新打开窗口并再次运行宿主。
- `SessionPolicy::StayResident`：零窗口也继续会话；原生宿主要求同时声明托盘，否则 `Host::open` 返回 `HostError::Session(SessionError::TrayRequired)`。
- `SessionCtx::request_show(key)` 在 `Event` / `Delivery` 中排队重新打开目录窗口；已关闭窗口重新运行 factory，隐藏窗口恢复同一 activation。`SessionCtx::request_quit()` 由同一队列显式结束会话：关闭全部 activation、释放待决关闭确认，并让之后的 `show` 返回 `WindowError::State`。排队动作按窗口请求先、会话动作后的顺序结算；直接调用 `Runtime::quit` 时尚未应用的窗口请求被丢弃。需要询问未保存内容时，应用先完成自己的确认再请求退出。
- 会话动作在窗口请求之后结算。headless 驱动同一 turn 先调用 `apply_window_requests`，再调用 `apply_session_requests`。
- 平台 session end 是另一条路径：应用停止新的窗口、dialog 和普通 UI 交付，执行一次有界 flush。它不能等待无限期的 worker，也不应在不可撤销的终止流程中再打开关闭确认。超时、失败和持久化结果具有明确的记录，不能靠一次写 sink 隐藏正在发生的超时；平台终止不在当前应用 quit 的范围内。

## UI 事件循环

UI 主事件循环负责处理窗口事件、UI command、布局和呈现。原生回调进入这个循环后，才能修改界面或启动模型操作。worker 经过事件循环桥接唤醒 UI。

菜单命令、鼠标激活、键盘快捷键、辅助动作与应用级命令进入同一个命令路径，各自携带来源与目标身份，防止一次操作被不同路径重复执行。应用级处理器通过 `Runtime::on_app_command` 在首个窗口打开或根树挂载前注册，可以在没有窗口时运行；窗口菜单声明项可以由它承接，目标窗口通过 `CommandEvent::window` 暴露，窗口派发只在窗口没有注册同一 id 时回退到应用级处理器，`CommandSource::Tray` 从不运行窗口处理器。系统拖放、菜单和模态宿主可能产生重入，模型与界面提交始终在已定义的命令边界内完成。

## 菜单与命令

窗口目录的 `MenuSpec` 构建原生菜单栏，`WindowCatalog::context_menu` 为同一窗口声明窗口级上下文菜单；托盘使用独立的 `TraySpec`，见「应用托盘」。三者共享命令 id 的派发规则与处理器解析，但各自拥有原生句柄，原生数字 id 只在构建它的那份菜单内编号。

```rust
let saved = runtime.setup(|| signal(false))?;
runtime.declare_windows(move |catalog| {
    catalog.window(WindowSpec::new("main").primary(), move |window| {
        window
            .on_command("file.save", |_| { /* 保存 */ })
            .expect("register file.save");
        window
            .on_command("view.status", |_| { /* 切换状态 */ })
            .expect("register view.status");
        window
            .on_command("edit.copy", |_| { /* 复制 */ })
            .expect("register edit.copy");
        window
            .on_menu_state(|command| match command.id() {
                "file.save" => MenuCommandState::new(saved.get(), false),
                _ => command.default_state(),
            })
            .expect("register the menu state callback");
        view! { <view /> }
    })?;
    catalog.menu(
        "main",
        MenuSpec::new()
            .item(MenuCommand::new("file.save", "Save").bind_shortcut("Ctrl+S")?)
            .separator()
            .command("view.status", "Show status"),
    )?;
    catalog.context_menu("main", MenuSpec::new().command("edit.copy", "Copy"))?;
    Ok(())
})?;
```

- `MenuCommand` 的稳定 id 是命令身份；原生数字 id 只在单个窗口内按声明前序分配。菜单栏与同一窗口的上下文菜单可以共享处理器，但 id 不能重复；上下文菜单不声明快捷键。声明期拒绝重复 id、重复归一化快捷键、无效快捷键与超过 65535 项的菜单。
- 菜单栏、快捷键、上下文菜单与托盘都进入 `Runtime::dispatch_command` / `dispatch_app_command`，分别标记 `CommandSource`。窗口处理器优先；窗口没有同一 id 时回退应用级处理器；`CommandSource::Tray` 从不运行窗口处理器。辅助技术的写动作走节点操作与 UIA 动作队列，不冒充菜单命令。
- `WindowCtx::on_menu_state` 每个 activation 至多登记一次，回调只返回 enabled/checked，不能写 Signal 或 Store。宿主在 `WM_INITMENU`、`WM_INITMENUPOPUP` 与派发前求值；失败时原生菜单保持原状，没有回调时使用 `MenuCommand` 的声明默认值。上下文菜单与托盘菜单不进入这条状态路径，保持声明默认值。
- `MenuCommand::bind_shortcut` 在声明期解析并归一化 Ctrl/Alt 组合；宿主为每个窗口建立 `HACCEL`，在 `TranslateMessage` 之前翻译。聚焦文本输入的 IME 组合与 Ctrl+A/Z/Y/C/X/V 优先；禁用命令在菜单与快捷键两个入口都不派发。
- 窗口级上下文菜单由 `WM_CONTEXTMENU` 打开；键盘调用把 `(-1,-1)` 换成客户区中心。presenter 在宿主借用之外用 `TrackPopupMenuEx(TPM_RETURNCMD)` 展示，返回的命令以 `CommandSource::ContextMenu` 派发一次；弹窗期间关闭或隐藏的 owner 丢弃返回值。
- 原生 `HMENU`、`HACCEL`、托盘 `HICON` 与 `NOTIFYICONDATAW` 的所有权、弹窗状态查询和托盘会话限制由 [ADR-0013](../adr/0013-menu-and-tray-host-services.md) 固定。隐藏测试是部分证据；菜单栏、快捷键与上下文菜单的 100%/150% 可见记录、以及托盘的单屏 150% 记录见 [stage-three 菜单栏验收](../实现/stage-three-菜单栏-验收.md)、[stage-three 快捷键验收](../实现/stage-three-快捷键-验收.md)、[stage-three 上下文菜单验收](../实现/stage-three-上下文菜单-验收.md) 与 [stage-three 托盘验收](../实现/stage-three-托盘-验收.md)。

## 应用托盘

托盘是应用级声明，不属于某个窗口。tooltip 与右键菜单在运行时启动前声明，菜单命令全部由应用级处理器承接：

```rust
runtime.on_app_command("app.hide", |event| {
    if let Some(window) = event.window() {
        window.request_hide().expect("queue the hide request");
    }
})?;
runtime.declare_tray(
    TraySpec::new("ZenUI Tray").with_menu(
        MenuSpec::new().command("app.hide", "Hide window"),
    ),
)?;
```

- `Runtime::declare_tray` 每个 Runtime 只接受一次，必须在首个窗口打开或根树挂载之前；tooltip 按 UTF-16 单元限制为 127，菜单拒绝重复命令 id、快捷键与超过 65535 项。宿主启动时校验每个菜单命令都有应用级处理器，缺失时 `Host::open` 失败并指出命令 id。
- 左键或键盘激活恢复目录中的可见焦点窗口；没有可见焦点时恢复 primary，primary 不在时选择任一存活窗口。有存活窗口时只在仍存活的 activation 中选择，已经关闭的窗口不会因托盘点击而重新打开；`StayResident` 零窗口时回退 primary 并重新运行 factory。
- 右键菜单以 `CommandSource::Tray` 派发一次，事件通过 `CommandEvent::window` 暴露选中的目标窗口；目标隐藏或被关闭确认挂起时仍合法，处理器可以排队 show/hide/close 请求。菜单选择与菜单栏、上下文菜单一样不产生第二次 `WM_COMMAND`。
- 默认 `QuitOnLastClose` 会话在最后一个窗口关闭后移除图标；`StayResident` 保留图标，零窗口时 worker 唤醒投递到托盘 HWND，左键恢复 primary。窗口重新出现时再次添加图标，`Host` 析构会尽力移除且重复移除安全。Explorer 重建通知区域时，宿主在 `TaskbarCreated` 广播后重新添加图标与 tooltip。
- 第一切片使用共享系统图标（`LoadIconW(None, IDI_APPLICATION)`），宿主与 presenter 都不销毁它；自定义图标资产与气球通知不在本切片。零窗口的托盘独存由 `SessionPolicy::StayResident` 显式开启，不是隐式默认；应用的 hide 请求是进入托盘的路径。原生最小化按钮自动隐藏到托盘不在本切片。
- Windows 11 默认把新图标放进通知区域溢出面板；宿主不修改用户的“始终显示”设置，也不承诺图标始终可见。tooltip、菜单与点击行为在溢出面板中仍由系统通知区域转发。

## 文件对话框的 anchor 与 job owner

原生文件对话框需要一个窗口作为宿主锚点，但选择结果之后启动的导入、保存或文件夹处理不一定属于这个窗口。SDK 把锚点与 job owner 分开：

```rust
let options = FileDialogOptions::open_files()
    .titled("Import tasks")
    .filter("Text files", ["txt"]);
let picker = window.request_file_dialog(options, window.app_task_scope())?;
picker.on_done(move |outcome| {
    match outcome {
        FileDialogOutcome::Picked(paths) => start_import(window, paths),
        FileDialogOutcome::Cancelled => Ok(()),
        FileDialogOutcome::Failed(error) => {
            status.set(error.to_string());
            Ok(())
        }
    }
})?;
```

保存与文件夹复用同一个入口：

```rust
let save = FileDialogOptions::save_file()
    .titled("Save tasks")
    .filter("Text files", ["txt"])
    .with_suggested_name("tasks.txt")
    .with_default_extension("txt");
window.request_file_dialog(save, window.app_task_scope())?;

let folder = FileDialogOptions::pick_folder().titled("Choose a folder");
window.request_file_dialog(folder, window.app_task_scope())?;
```

- `open_file()` / `open_files()` 决定单选或多选；`save_file()` 使用标题、过滤器、建议文件名（`with_suggested_name`）与默认扩展名（`with_default_extension`），`pick_folder()` 只使用标题并忽略过滤器、建议文件名与默认扩展名。标题与过滤器由应用提供，框架不注入默认扩展名；保存与文件夹都是单路径契约，`allows_multiple()` 为 false。
- 返回值是普通 `Task<FileDialogOutcome>`；continuation 在 `Delivery` turn 运行，可以提交模型或写仍存活的 UI Signal。已选择的结果按任务所有权交付，不由 anchor 决定。
- `window.task_scope()` 让选择结果随 activation 关闭而取消或 stale；`window.app_task_scope()` 允许选择结果在 anchor 关闭后到达应用级 continuation。anchor 不会隐式升级或降级 job。
- `request_file_dialog` 只接受 `Event` / `Delivery`，要求锚点存活、可见、没有待决关闭，scope 来自同一 runtime；隐藏窗口、factory/memo 阶段、其它窗口的 scope 与旧 activation 都明确拒绝。同一 turn 的关闭加请求由宿主在取请求时重新检查，不会重定向到重开的窗口。
- 用户取消是 `Cancelled`，不是错误；对话框失败是 `Failed`。失败是值，应用决定 UI 文案。
- 保存和文件夹结果都是单个路径；`FileDialogOutcome::Picked` 仍携带列表以兼容打开多选。应用在保存对话框返回后拥有写入；宿主不写应用数据。
- 原生呈现是 UI 线程上的一次模态调用，一个 Host 同时只呈现一个对话框。Windows 宿主按 kind 分派：打开文件使用 `IFileOpenDialog`，保存使用 `IFileSaveDialog`，文件夹使用带 `FOS_PICKFOLDERS` 的 `IFileOpenDialog`。保存和文件夹按单路径契约配置；文件夹忽略过滤器、建议文件名与默认扩展名。宿主在完成 `Picked` 之前按 `allows_multiple()` 校验路径数量，数量不符变成 `Failed`。隐藏宿主在没有注入 presenter 时对所有 kind 返回 `Unsupported`；测试注入的 presenter 仍走同一条交付路径。

宿主后端在消息循环层用 `Runtime::take_file_dialog_requests` 取出请求、呈现对话框，再用 `Runtime::complete_file_dialog_request` 恰好一次完成。`take` 先结算锚点已失效的请求：窗口所有权任务取消，应用所有权任务以 `AnchorClosed` 完成。`complete` 只保存结果，不运行 continuation；交付仍发生在 `drive_tasks` 的 `Delivery` turn。`settle_tasks` 只等待 worker，等待中的 picker 不会让它阻塞。

用意图决定生命周期：

| 场景 | 适合的 owner |
| --- | --- |
| 行预览、局部动画、窗口临时请求 | 当前 window activation |
| 跨窗口的导入、保存、文件夹处理、共享同步、全局错误记录 | application root |
| 只可在进程存活期间运行的 host service | application session |

`task_scope()` 必须来自某个定义清楚的执行位置。窗口 factory 中取得的 scope 不能默认为 app lifetime，文件对话框的 anchor 也不能隐式把 job 转到 app root。宿主任务契约见 [ADR-0008](../adr/0008-file-picker-host-tasks.md)，文件对话框家族与 rename 见 [ADR-0009](../adr/0009-file-dialog-family.md)。

## 文件拖放的事件与所有权

文件拖放是窗口事件，不是文件对话框。`WindowCtx::on_drop` 在窗口 factory 中注册一次；处理器收到 `DropEvent`，按源顺序读取路径：

```rust
window.on_drop(move |drop| {
    let paths = drop.into_paths();
    let result = window
        .app_task_scope()
        .spawn(move |_| read_import(&paths))
        .and_then(|task| {
            task.on_done(|titles| {
                // 提交应用模型，或写仍存活的 UI Signal。
                Ok(())
            })
        });
    if let Err(error) = result {
        status.set(error.to_string());
    }
})?;
```

- 注册只发生在窗口 factory 中，每个 activation 一次；重复注册或在 factory 外注册返回 `WindowError::State`。关闭窗口释放处理器，重新打开需要新的注册。
- `DropEvent::window()` 给出接收的 activation，`paths()` 借用有序路径，`into_paths()` 取走。重复路径、Unicode、非 BMP 字符与长路径原样保留，不做去重、规范化或扩展名过滤；文件夹也是普通路径，由应用决定是否接受。
- `Runtime::drop_files` 在运行处理器前拒绝外部 Runtime、已关闭/过期的 activation、隐藏窗口、等待关闭确认的窗口、空列表与没有处理器的窗口，分别返回 `DropError` 的 `WrongRuntime`、`Stale`、`Hidden`、`Suspended`、`Empty` 与 `NoHandler`。被拒绝的投递不写模型、不启动任务，也不进入 `Phase::Event`。
- 原生宿主只为可见且注册了处理器的窗口建立 OLE target。源必须提供 `CF_HDROP` 并允许 COPY；窗口被禁用（例如原生文件对话框打开的 owner、等待关闭确认的父窗口）时，拖动返回 NONE。确认窗口本身不被禁用：本示例没有为它注册处理器，所以没有 target；若应用注册了处理器，target 会在拖动阶段接受，但 drain 时 `Runtime::drop_files` 以 `Suspended` 拒绝，处理器不会运行。非文件数据、MOVE/LINK 与空文件列表在处理器前被拒绝，因此 `on_drop` 只会看到文件列表。
- 处理器在 `Phase::Event` 中运行一次，可以写 Signal/Store、排队窗口请求，并用 `window.task_scope()` 或 `window.app_task_scope()` 启动任务。拖放本身不创建任务、没有取消句柄，也没有 pending 状态；需要跨窗口或 anchor 关闭后继续的读取必须显式使用应用所有权 scope。
- 处理器 panic 被 contain 为 `DropError::HandlerPanicked`，运行时状态保持可用；直接调用 `Runtime::drop_files` 的后续投递仍可运行，原生宿主把这次失败报告为 `HostError::Drop`。原生回调与 drain 之间窗口被隐藏、挂起或关闭时，这次投递按正常拒绝处理。
- 本切片只处理文件列表；文本、URL、图片、MOVE/LINK、拖放位置、drag image 与程序化拖动都不在契约内。窗口整体接受拖放，不按坐标命中子元素。

契约见 [ADR-0016](../adr/0016-ole-file-drop-target.md)，100% 与 150% 的真实资源管理器验收见 [stage-three 文件拖放验收](../实现/stage-three-文件拖放-验收.md)。

## Worker 和 UI 的边界

worker 只取得可 Send 的 job 与结果通道：

```text
选择文件 -> 在 UI 侧创建 ImportJob
         -> worker 读取、解析、生成 PreparedImport
         -> generation-checked UI continuation
         -> 有效的模型事务
```

窗口或 UI 组件的 handle 不应直接变成 worker 的数据解析权限；隐藏窗口暂停呈现，旧 surface 的写入随当前呈现代际结束。

唤醒回调只通知宿主“有事可做”，不交付结果。宿主被唤醒后仍需回到 UI 事件循环调用 `drive_tasks`，在 `Delivery` turn 中执行 continuation；尚未登记 continuation 的结果会保持等待，直到登记为止。回调 panic 会被捕获，不会终止 worker，也不会丢失已发送的结果。关闭与完成竞争时，如果 worker 在关闭前已观察到未取消，唤醒可能发生在关闭之前；该结果仍按旧 activation 丢弃，不会交付到后续 activation。

如果 app import 在窗口关闭后完成，app 级模型可以继续更新，旧窗口 delivery 仍被丢弃。重新打开 Main 后读取的是共享模型的最新状态，不会收到旧窗口或旧 renderer 的延迟回调。

## Host 与渲染的退出顺序

窗口退出先取消输入、IME、语义事件和任务交付，再停止呈现与资源提交，随后释放子窗口 / dialog 和该 activation 的本地状态。应用级 AppState 和 AppTasks 不在其中一并销毁。

device loss、surface recreation 和 renderer fallback 属于渲染恢复，不需要回滚一个无关的模型事务。普通关闭确认协议与平台不可撤销的销毁或 session end 是不同路径，不能强行让两种场景共用一次 Allow 调用。

## Windows 宿主

`zenui-windows` 是第一个平台宿主：一个 HWND 对应一个 activation，关闭窗口时释放该 activation，重开时 window factory 重新执行。宿主用 `windows` crate 直接创建 Win32 窗口，启用 per-monitor v2 DPI awareness，并通过 DX12 surface 呈现 `zenui-render` 的场景；硬件适配器不可用时回退 WARP。

- `Host::open(Runtime, HostConfig)` 从一个已声明窗口目录的 Runtime 创建宿主：目录提供每个窗口的标题与初始逻辑尺寸，`HostConfig` 携带初始可见性、外观与可选的文本资产。`HostConfig::with_text_assets(TextAssets)` 在创建任何原生窗口之前注册并校验固定字体；无效资产返回 `HostError::TextAssets`，不产生 HWND；没有配置资产时沿用系统字体集合。宿主为每个存活窗口创建一个 HWND 与 DX12 surface，共享 device、queue 与 renderer；`run` 显示所有已打开窗口，`show` / `hide` / `close` 同步运行时状态；默认会话在最后一个窗口关闭后结束消息循环，`StayResident` 在零窗口时继续接收托盘与 worker 消息，直到显式退出。目录中的逻辑尺寸按系统 DPI 换算为初始物理客户区；`HostConfig::appearance` 设置初始 `Light`/`Dark`，宿主每帧按该窗口快照外观选择调色板。应用通过 `WindowCtx::appearance()` / `set_appearance()` 读取和切换外观；外观是已提交状态，所有窗口共享，切换会失效依赖它的 memo 并重绘每个窗口，但保留各自焦点、caret、selection 与编辑状态。surface 只接受 `Bgra8Unorm`；仅提供 sRGB BGRA 的表面会被明确拒绝，因为调色板字节已经按 sRGB 编码。错误通过 `HostError` 返回，不 panic。
- `SystemPreferences` 是宿主输入的高对比度与文本缩放值：`high_contrast: bool` 与 100–225 的整数百分比，越界回退 100。可见宿主在启动与 `WM_SETTINGCHANGE` 时采样 `SPI_GETHIGHCONTRAST` 与 `HKCU\Software\Microsoft\Accessibility\TextScaleFactor`；`HostConfig::with_system_preferences` 设置初始值，`Host::set_system_preferences` 供嵌入方替换，`Host::system_preferences` 读取当前值。隐藏宿主默认关闭/100%，不读取真实系统设置。高对比度开启时，场景使用 `RenderPalette::high_contrast` 与采样到的 `GetSysColor` 颜色，覆盖应用明暗外观的语义角色；文本缩放进入 `SceneEnv`，放大字号、行高、`em` 几何、caret/selection、命中与滚动范围。偏好变化只标记窗口重绘并重建场景：不改呈现版本、不运行事务、不派发 `on:input`，焦点、caret、selection 与本地编辑值保留，滚动偏移按新内容重新夹取。显式字面颜色与固定 `px` 几何不随偏好变化。契约见 [ADR-0022](../adr/0022-system-preferences.md)，可见证据见 [系统偏好验收](../实现/stage-three-系统偏好-验收.md)。
- 原生菜单栏在 `CreateWindowExW` 前由目录的 `MenuSpec` 构建，命令 id 按声明前序分配；创建、`resize` 与 DPI 换算都按菜单存在性计算非客户区。每个 activation 可在 factory 中用 `WindowCtx::on_menu_state` 登记至多一个只读状态回调，关闭窗口时释放，重新打开必须重新登记。宿主在 `WM_INITMENU`/`WM_INITMENUPOPUP` 按命令调用 `Runtime::menu_state` 并把返回的 enabled/checked 写回原生项；没有回调时使用 `MenuCommand` 的声明默认值。回调在只读作用域内运行，Signal 写与 Store 事务被拒绝为 `MenuStateError`，panic 被 contain；一次初始化中任一回调失败时菜单保持原状。`MenuCommand::bind_shortcut` 在声明期解析并归一化快捷键，同一窗口的重复快捷键是目录错误；宿主为每个窗口构建 `HACCEL`，`run`/`pump` 在 `TranslateMessage` 之前翻译，匹配时以 `CommandSource::Accelerator` 走同一条命令路径。聚焦文本输入的 IME 组合与 Ctrl+A/Z/Y/C/X/V 继续走编辑器路径。`WM_COMMAND` 只接受 `lParam=0` 与 `HIWORD=0/1`，派发前再次求值状态，禁用项在菜单与快捷键两个入口都不运行。`WindowCatalog::context_menu` 为窗口声明窗口级上下文菜单；它与菜单栏共享处理器，但命令 id 不能重复，也不接受快捷键。宿主在 `WM_CONTEXTMENU` 中把 presenter 与声明移出 `Host`，在借用之外用 `TrackPopupMenuEx(TPM_RETURNCMD)` 打开 `CreatePopupMenu` 构建的菜单；键盘调用的 `(-1,-1)` 换成客户区中心。菜单关闭后宿主重新借出，presenter 归还，返回的命令只在窗口仍接受输入时以 `CommandSource::ContextMenu` 派发一次；弹窗期间关闭或隐藏的 owner 丢弃返回值。弹窗期间宿主跳过菜单栏的 `WM_INITMENU`/`WM_INITMENUPOPUP` 状态应用，上下文菜单保持声明默认 enabled/checked，两套数字命令 id 不互相命中。隐藏宿主默认不安装原生 presenter，测试通过 `Host::set_context_menu_presenter` 注入 fake。设计时机与证据边界见 [stage-three 菜单栏验收](../实现/stage-three-菜单栏-验收.md)、[stage-three 快捷键验收](../实现/stage-three-快捷键-验收.md) 与 [stage-three 上下文菜单验收](../实现/stage-three-上下文菜单-验收.md)。
- 应用托盘由 `Runtime::tray()` 的声明驱动：宿主创建一个从不显示的顶层 `ZenUIHostWindow` 托盘 HWND，并在创建图标前注册 `TaskbarCreated`。`TRAY_CALLBACK` 是宿主的私有消息 `WM_APP + 4`，与 worker 唤醒分开，由托盘 HWND 在窗口过程里路由；左键与键盘激活在目录存活窗口中选目标（可见焦点窗口、primary、其余第一个），通过 `Runtime::show` 恢复；`StayResident` 零窗口时回退 primary 并重新运行 factory；目标原生窗口已最小化时先 `ShowWindow(SW_RESTORE)`。右键回调在 `lParam` 低字携带事件、`wParam` 携带物理屏幕坐标（`NOTIFYICON_VERSION_4`）；宿主把 presenter 与菜单移出 `Host`，在借用之外用 `TrackPopupMenuEx(TPM_RETURNCMD | TPM_RIGHTBUTTON)` 展示，返回后归还 presenter，并以 `CommandSource::Tray` 派发一次应用级命令。presenter 调用被 contain，panic 转为 `HostError::TrayPresenter`，不穿过窗口过程或 `Drop`。原生 presenter 用 `NIM_ADD` + `NIM_SETVERSION(NOTIFYICON_VERSION_4)` 添加图标，`NIM_MODIFY` 更新标准 tooltip，`NIM_DELETE` 移除；默认会话在最后一个窗口关闭后移除图标；`StayResident` 会话保留图标，并在零窗口时把 worker 唤醒投递到托盘 HWND。窗口重新出现时再次添加，`TaskbarCreated` 到达托盘 HWND 时重新添加，`Host` 析构时尽力移除且不重复删除。shell 可能用 `SendMessage` 投递托盘回调，宿主在每次回调后向托盘 HWND 投递 `WM_NULL`，保证恢复/退出后的窗口同步发生。可见宿主安装原生 presenter；隐藏宿主默认没有 presenter，测试通过 `Host::set_tray_presenter` 注入 fake。图标句柄来自系统共享的 `IDI_APPLICATION`，不使用 `DestroyIcon`。托盘证据见 [stage-three 托盘验收](../实现/stage-three-托盘-验收.md)，会话证据见 [stage-three 会话验收](../实现/stage-three-会话-验收.md)。
- 应用会话由 `Runtime::session_policy` 驱动：`Host::open` 拒绝没有托盘的 `StayResident`；`Host::run` / `pump` 用会话而不是窗口数判断是否继续，零窗口常驻时 worker 唤醒回退到托盘 HWND。每次输入或交付后，宿主先结算窗口请求，再结算会话动作；`SessionCtx::request_quit` 在这里关闭全部 activation，随后同步移除 HWND 与托盘图标。默认策略仍在最后一个窗口关闭后结束循环，但退出时机现在来自声明的策略。headless 调用方按同一顺序调用 `apply_window_requests` 与 `apply_session_requests`。
- `Host::run` 显示窗口（或保持隐藏）并进入消息循环。窗口过程是输入与绘制的入口：`WM_SIZE` 到达后立即按新客户区重排、重配置 surface 并呈现，使 DWM 不会把上一帧拉伸到新尺寸；`WM_GETDPISCALEDSIZE` 按新旧 DPI 比例换算物理客户区，再按新 DPI 加上非客户区，使 DPI 变化后的逻辑客户区保持不变（最大化/最小化交回默认过程）；该消息不保证每次送达，`WM_DPICHANGED` 仍按系统建议矩形调整并同步重绘，作为兜底；`WM_PAINT` 只处理有实际更新区域的曝光与其它失效。系统的模态拖动/缩放循环直接调用窗口过程，消息循环在此期间收不到消息；因此 `run` / `pump` 在派发期间通过 `GWLP_USERDATA` 暴露裸指针，让窗口过程完成重排与输入处理，指针由 guard 在返回或 panic 展开时清除。`WM_CLOSE` 走运行时关闭策略：Immediate 释放 activation；Confirm 建立 epoch 并显示确认窗口，父窗口保持存活但等待 Deny/Allow。消息循环在派发返回后销毁已释放窗口的 HWND，并在会话结束时退出：默认策略要求仍有存活窗口，`StayResident` 直到显式退出。场景逻辑尺寸来自客户区物理像素除以 DPI scale。HWND 的销毁推迟到窗口条目析构，保证 surface 存活期间句柄有效。
- 指针瞬态由宿主拥有，不进入 presentation snapshot：`WM_MOUSEMOVE` 经最近一次场景的 `hit_test` 得到最上层启用元素作为 hover，`TrackMouseEvent(TME_LEAVE)` 只注册一次，`WM_MOUSELEAVE` 清除 hover；`Scene::build_with` 通过 `SceneEnv` 读取 hovered、pressed 与键盘模态。每次重建场景前都用最后的指针位置重新命中，节点被过滤、重排或移走后不会残留旧 hover/press。
- 整页滚动也是宿主拥有的呈现状态：每个 activation 保存一个已夹取的 `i32` 逻辑像素偏移，它是持久的 presentation 环境值，不是随事件的 hover/press/键盘模态瞬态，也不是快照属性或应用状态；滚动不运行事务，不改变模型、焦点、caret 或 selection。`WM_MOUSEWHEEL` 归约到该 activation 私有的有符号 `i64` 定点累加器与锚点：`lines_per_notch` 在 activation 内缓存（默认 3，`WM_SETTINGCHANGE` 刷新），一个 notch（`WHEEL_DELTA` = 120 单位）为 `lines_per_notch × 24` 逻辑像素；系统 page-scroll 哨兵值 `WHEEL_PAGESCROLL` 使一个 notch 等于一次 PageDown/PageUp；设置为 0 时禁用滚轮并清零累加器。每个事件把 `delta_units × notch_pixels` 加入累加器，取 `pixels = 累加器 / 120`（向零截断），请求 `applied_offset − (pixels − anchor)`，再把锚点设为 `pixels`；正向 notch 减小偏移，不足一像素的 residue 留在累加器中，双向对称累积。累加器与锚点在场景夹取滚轮请求时、以及偏移由滚轮之外的操作改变时清零（键盘滚动、显露、resize、快照或内容重新夹取、hide/show），因此边界处被夹掉的滚轮距离被丢弃而不会在反转时回吞第一格；`lines_per_notch` 改变与 close/reopen 同样清零，从不跨窗口共享。到达边界时被夹取的滚轮距离丢弃，事件仍被消费，滚动不向父容器传递，也不 overscroll。报告像素级精度的平台把 delta 换算成逻辑像素后放进同一 activation 的另一个 `i64` 定点缓冲，遵循同样的差值/清零规则，两种累加单位从不混用。PageUp/PageDown 滚动 `max(1, floor(viewport_height − 24))` 逻辑像素并保留一行 24 像素重叠，Home/End 到零/最大值；每个按键重复是独立一步，最大偏移为零时滚动键不被消费。聚焦编辑器的编辑键优先（Home/End 编辑文本，PageUp/PageDown 仍翻页），组合期间编辑键与翻页键归 IME。宿主把偏移放进 `SceneEnv`，采用场景夹取后的实际值作为后续相对步的起点，并按平移后的场景重新命中 hover。输入只复用快照 revision 与环境代际都与当前一致的场景；构建前与派发前都会用最后指针位置重新命中。press 是 capture-based，滚动不按新的 hover 重新评估，但目标已离开挂载场景或被禁用时立即清除。hover、pressed 与 caret 闪烁是逐事件宿主瞬态；滚动偏移是上面定义的持久呈现环境值，不是瞬态。空白处按压、指针移动与闪烁同样只读取缓存。`Runtime::presentation_revision()` 未变时宿主复用缓存的 presentation snapshot，只重建场景，不重建也不复制运行时快照，因此这些瞬态不增加快照构建，Node ID 保持不变；改变焦点、caret、组合或模型的操作会改变版本并按需重建一次。`Runtime::presentation_builds()` 暴露累计快照构建次数供验收与基准测量。hide/show 保留偏移并按当前内容重新夹取，close/reopen 归零；resize、DPI 变化、surface/设备重建保留逻辑偏移且不按 Window scale 重新缩放；快照变化（插入、删除、过滤、重排）保留存储的已应用偏移并重新夹取，本里程碑没有 scroll anchoring 或 follow-the-end。设计见 [ADR-0010](../adr/0010-scroll-is-presentation-state.md)，可见证据见 [stage-three 宿主滚动验收](../实现/stage-three-宿主滚动-验收.md) 与 [stage-three 滚动总验收](../实现/stage-three-滚动总验收.md)。
- 焦点与 caret 显露同样由宿主拥有：`TurnReport::reveal` 报告本次 turn 的焦点、caret/selection 与组合变化，宿主只在任一变化时置位 `reveal_requested`；没有位置变化的按键不会把视口拉回聚焦输入。构建时用 caret 几何（不存在时用元素边框盒）按 ADR-0010 的规则夹取一次并重建，caret 在第一次重建后才出现时再重复一次，最多两次重建；超高元素顶部优先，残留越界被接受。显式滚轮与翻页键清除待决显露，滚动本身永不移动焦点或 caret。隐藏 smoke 与可见证据见 [stage-three 焦点显露验收](../实现/stage-three-焦点显露-验收.md)。
- 视口右缘的覆盖层滚动条由场景度量推导并在内容之后绘制：thumb 高度按 viewport/content 缩放且最小 24 逻辑点；轨道容不下最小 thumb 或 thumb 会填满轨道（没有拖动行程）时不绘制。轨道与 thumb 不新增元素、不占布局。指针在内容命中之前先命中滚动条：thumb 按下捕获指针并拖动，偏移按指针在剩余行程中的比例夹到 `[0, max]`；轨道点击向点击一侧翻一页；捕获丢失、焦点丢失、隐藏/禁用与关闭都结束拖动且不留下按压或悬停。滚轮、拖动与键盘共享同一个偏移，显式滚动只重建场景。滚动条按下不取消 IME 组合（滚动永不提交或取消组合）；组合期间翻页、Home/End、方向键与 Backspace/Delete 归 IME，宿主不编辑、不显露也不滚动。绘制细节见 [渲染场景](渲染场景.md)，可见证据见 [stage-three 滚动条验收](../实现/stage-three-滚动条-验收.md)。
- 窗口化 `For` 的挂载窗口也由宿主同步（[ADR-0011](../adr/0011-windowed-for-mounting.md)）：场景经 `Scene::row_bands()` 报告行带几何，宿主按已应用偏移与视口高度算出每个行带的 `(first, count)`；聚焦行被窗口留在外面超过一行时，宿主先 blur 并取消组合，再把整批目标交给 `Runtime::set_row_windows`。批量在一个原子结构 turn 里预校验：任一行带失效、属于其他窗口或重复出现时整批不应用；任一行工厂失败时整批回滚到旧窗口。运行时挂载进入窗口的行、卸载离开窗口的行并调整上下 spacer，快照版本变化一次，宿主通常额外重建一遍场景（blur 处理器重写树时的有界重试可再多建一遍，见 [ADR-0011](../adr/0011-windowed-for-mounting.md)）；场景构建（`ensure_scene`）是纯构建，永不运行行工厂。行工厂拒绝新窗口时，运行时已回滚请求，宿主保留已提交场景并通过 `Host::take_diagnostics` 报告，不把可恢复失败升级成会话退出。行窗口不变时滚动只改 `SceneEnv` 偏移，不重建快照；视口下缘跨入新行（窗口的 trailing `count` 增加）或首行变化时每帧至多一次窗口更新，挂载成本与总行数无关。行窗口变化不重置滚轮 residue，因为它不改变模型顺序。窗口外的行没有 Scene 元素与 Node ID，旧 ID 报告 `Stale`；Tab 只遍历已挂载行。headless 运行时从未收到行窗口时从第 0 行挂载 32 行默认窗口。隐藏 smoke 覆盖挂载窗口随 End/Home 推进、行重新进入时获得新 Node ID、Tab 在窗口边界离开列表与远距离滚动 blur 并取消组合；可见证据见 [stage-three 窗口化 For 验收](../实现/stage-three-窗口化-for-验收.md)。
- 上述瞬态与外观的分工（宿主拥有 hover/press/模态，外观进入快照，场景统一解析样式）见 [ADR-0006](../adr/0006-presentation-transients-and-style-resolution.md)。
- 输入按接收消息的 HWND 路由到该窗口的树与瞬态；`WM_LBUTTONDOWN` 把物理坐标按 scale 换算成逻辑坐标，再按元素类型处理：文本输入在按下时聚焦并按 `SceneElement::caret_index` 放置 caret；button 与 checkbox 只记录 press 目标并 `SetCapture`，不立即激活；容器与文本清除焦点。`WM_LBUTTONUP` 先取走 press 目标（`ReleaseCapture` 会同步送出 `WM_CAPTURECHANGED`），只有松开仍命中同一个启用节点时才派发 button `click` 或 checkbox `change`；拖出原目标后松开不激活。捕获丢失、焦点丢失与关闭都清除 press。disabled 元素不悬停、不聚焦、不激活，也不改变焦点。派发只依赖 Node ID；宿主不保存 caret、selection 或控件状态。静态元素缺少 handler、不可聚焦或派发中被重挂载时的拒绝是正常交互结果。
- 待决关闭的父窗口在运行时输入仲裁中挂起，宿主同步用 `EnableWindow` 禁用其 HWND，并在禁用前取消 IME 组合与指针瞬态；Deny 后重新启用并恢复父窗口焦点。确认窗口的 X 走 `WM_CLOSE`，Escape 在非组合状态下等价于 Deny；组合中的 Escape 仍只取消组合。关闭回复与 show 请求一样在消息处理后结算，因此宿主不会在确认窗口中保留第二套关闭状态。
- UIA 事件从相邻两次发布树的差异产生，顺序为结构、属性、焦点。结构事件按父节点比较子集与顺序：ChildAdded 发在新增子节点，ChildRemoved 在父节点携带被移除的 runtime ID，ChildrenReordered 在父节点；新子树只报告顶层新增。IsEnabled、ToggleState 与 Value 只比较两次都存在的节点；根 IsEnabled 由宿主窗口 provider 通知，规划器不重复投递。只有前台窗口投递焦点事件，后台焦点变化在激活时不补发；焦点清空没有 UIA 事件，客户端以 `GetFocus` 为空观察。指针 hover/press 与滚动几何不改变树，因而不产生事件。事件在发布锁释放后投递，单条失败不阻断后续；可见证据见 [stage-three 辅助技术事件验收](../实现/stage-three-辅助技术事件-验收.md)。
- UIA 文本 pattern 由已发布树中的 Edit 节点暴露，文档取已提交值并排除 preedit。UIA 偏移是 UTF-16 code unit，provider 在调用线程换算成运行时字符偏移；GetText、GetSelection、GetVisibleRanges、GetBoundingRectangles 与 GetEnclosingElement 读取当前发布，DocumentRange 的矩形是元素文本区域，折叠范围只有当前位置的 caret 有矩形，非折叠 selection 返回场景的逐行 selection 矩形。Select 只入队 `SetSelection`；UI 线程重验启用、`on:input` 与组合状态后调用 `Runtime::set_selection_node`，不派发 `on:input`，组合中、禁用与只读输入拒绝写入。查找、移动、扩展、比较、多选、滚动与子 range 方法返回 `UIA_E_NOTSUPPORTED`，不声明富文本或受保护文本能力。可见证据见 [stage-three 辅助技术文本验收](../实现/stage-three-辅助技术文本-验收.md)。
- 每个窗口的 fragment root、树派生、provider 线程与动作队列由 [ADR-0012](../adr/0012-uia-derived-tree-and-action-queue.md) 固定：provider 只读当前不可变发布；`WindowCtx::runtime_id()`、`WindowCtx::activation_id()` 与 `NodeId::runtime_id()` 暴露 runtime 身份，provider 创建时注入 `(runtime, ActivationId)`，Node 与 Scroll 请求进入同一个每窗口 FIFO（共享 1024 上限、顺序与清空），UI 线程先按身份、再按最新快照重验；隐藏、关闭中或零客户区窗口没有树并清空队列，关闭确认的父窗口保留树但报告禁用，确认窗口有独立根。窗口根在同一份场景几何上暴露垂直 `ScrollPattern`：view size 为 viewport/content 百分比，百分比由已应用偏移换算，水平固定为 `NoScroll`；`Scroll` 复用键盘翻页与滚轮行步长，`SetScrollPercent` 把 0..100 四舍五入到整数逻辑像素后夹取。没有滚动条 NodeId、`ScrollItemPattern` 或水平滚动；MSAA 桥、SelectionItem 与虚拟化 item pattern 是显式延后项。证据边界：进程外 UIA 客户端与 Inspect 的 100%/150% 结果是主证据，Narrator 的逐字短语来自 Speech Recap，隐藏 smoke 与 CI 只是部分证据；总览见 [stage-three 辅助技术合同与朗读验收](../实现/stage-three-辅助技术总验收.md)。
- 宿主拥有唯一的 OLE 套间：首次需要时调用 `OleInitialize`，`S_OK`/`S_FALSE` 都恰好配对一次 `OleUninitialize`，`RPC_E_CHANGED_MODE` 分别映射为文件对话框的 `Unsupported` 与拖放的 `DragDropError::Unsupported`。隐藏宿主不为文件对话框或拖放初始化 OLE；UIA 根 provider 请求仍会按既有辅助技术路径初始化同一套间。注入 presenter 的隐藏宿主不因文件对话框初始化 OLE。文件对话框与 OLE 拖放共用这个套间；剪贴板读写直接使用 `OpenClipboard` 系列 API，不需要 OLE。该初始化取代 [ADR-0008](../adr/0008-file-picker-host-tasks.md) 的 `CoInitializeEx` 段落，详见 [ADR-0016](../adr/0016-ole-file-drop-target.md)。
- 文件对话框走宿主服务：`Host` 在消息循环层按 FIFO 一次服务一个请求，把 presenter 移出 `Host` 后在借用之外调用，再恢复并完成请求。原生 presenter 在宿主 OLE 套间里按 kind 创建 `IFileOpenDialog` 或 `IFileSaveDialog`：打开请求映射标题、过滤器与多选；保存请求追加 `FOS_OVERWRITEPROMPT`，应用标题、过滤器与 1-based type index、建议文件名和默认扩展名；文件夹请求追加 `FOS_PICKFOLDERS` 且不配置过滤器、type index、建议文件名或默认扩展名。有效 shell 默认值只 OR 不清除，`FOS_NOTESTFILECREATE` 保持未设置。用户取消映射为 `Cancelled`，其它 `Show` 错误映射为 `Failed`。宿主在完成前校验 `Picked` 的路径数量。隐藏宿主默认完成 `Unsupported`；`Host::set_file_dialog_presenter` 注入的 presenter 在隐藏模式也运行，是 CI 的 seam。对话框期间 owner 由 shell 禁用，宿主不另行 `EnableWindow`；嵌套消息仍会派发，因此 worker 结果可以在对话框打开时交付并重绘。shell 对话框只能由用户关闭，程序化取消是后续工作；设计与证据见 [ADR-0009](../adr/0009-file-dialog-family.md)、[stage-three 文件对话框验收](../实现/stage-three-文件对话框-验收.md) 和 [stage-three 保存与文件夹验收](../实现/stage-three-保存与文件夹-验收.md)。
- 文件拖放为每个可见且注册了 `on_drop` 的窗口建立一个 OLE `IDropTarget`；隐藏宿主不建立 target、也不为拖放初始化 OLE。窗口隐藏或关闭时撤销注册，重新显示或重开得到新 target 与空队列。`DragEnter`/`DragOver` 只在窗口启用、数据提供 `CF_HDROP` 且源允许 COPY 时返回 COPY，其它情况返回 NONE；`Drop` 用 `DragQueryFileW` 按序提取路径、释放 `STGMEDIUM` 后把列表排入窗口队列。COM 回调不运行用户代码，只投递 `WM_APP + 5`；宿主在 UI 线程 drain、调用 `Runtime::drop_files`，随后结算窗口请求并重绘。模态 shell 对话框与待决关闭的父窗口通过原生窗口禁用拒绝拖放；确认窗口本身保持启用，本示例没有为它注册处理器，因此没有 target（若注册，drain 以 `Suspended` 拒绝）。契约见 [ADR-0016](../adr/0016-ole-file-drop-target.md)。
- 键盘消息把输入模态切到键盘，指针按下切回指针；`focus-visible:` 只在键盘模态下匹配焦点元素，因此 Tab 聚焦与鼠标聚焦可以有不同的可见焦点样式。
- 聚焦编辑器的保留快捷键由 `shortcuts` 模块的单一策略函数决定：只有聚焦可编辑输入、按下 Ctrl 且没有进行中的 IME 组合时才返回动作，组合优先让 IME 消费按键。Ctrl+A 接到全选，Ctrl+Z/Y 接到运行时的 undo/redo（一次按键恰好一次 `on:input`，值、caret 与 selection 按历史条目恢复）；连续单字符输入合并为至多 64 个字符的有界撤销步，空白附在前一个词上，移动、焦点变化、删除、多字符插入、组合、撤销/重做与外部替换都会开始新步。Ctrl+C 把已提交选区写入剪贴板且不派发 `on:input`；Ctrl+V 读取 `CF_UNICODETEXT`，过滤单行输入不接受的全部控制字符后，通过同一次插入 reducer 替换选区或插入 caret，一次粘贴恰好一次 `on:input`。Ctrl+X 复用同一条写入路径，只有 provider 确认写入成功后才删除选区；写入失败或没有 provider 时文本、选区与 caret 都不变，因此不会在剪贴板失败时丢失文本。隐藏宿主没有剪贴板 provider 时按键不产生系统剪贴板 I/O；可见宿主安装原生 provider，嵌入方用 `Host::set_clipboard_provider` 注入自己的实现。契约见 [ADR-0015](../adr/0015-clipboard-host-capability.md)，可见证据见 [stage-three 文本编辑历史验收](../实现/stage-three-文本编辑历史-验收.md) 与 [stage-three 剪贴板验收](../实现/stage-three-剪贴板-验收.md)。
- `Host::pump` 处理所有已排队消息后立即返回，返回宿主会话是否已结束，供嵌入外部消息循环或测试驱动单次输入；`Host::scene(key)`、`Host::presentation(key)` 与 `Host::read_frame(key)` 分别暴露该窗口的场景、已提交快照与像素。每条输入消息与每次任务交付结束后，宿主结算运行时排队的窗口请求；新窗口在同一轮同步中创建 HWND、配置 surface 并首次呈现，随后由修订号驱动其余窗口重绘。窗口请求生效或 `Host::show` / `hide` / `close` 之后，若前台已属于本宿主，宿主把运行时焦点窗口置前（`SetForegroundWindow`）并显式结算被抑制的 `WM_KILLFOCUS`；隐藏模式、已关闭窗口或前台属于其它进程时不动前台，运行时焦点与输入路由不受系统前台策略影响。
- `zenui_demo::open_todo_window` 声明 `main`、`details` 与 `close` 三个窗口并只打开 primary。主窗口采用 `Confirm` 关闭策略：关闭处理器在草稿为空时立即 Allow；草稿非空时显示 `confirmation_for("main")` 的确认窗口，Continue editing 回复 Deny，Discard draft 清空共享草稿并回复 Allow。主窗口工具栏的 Details 动作通过 `request_show("details")` 打开或聚焦摘要窗口；Details 共享 remaining、过滤结果与行标题，拥有自己的焦点、caret、草稿和 note 输入，并提供 Hide / Close 动作验证隐藏恢复与关闭重开都不触碰主窗口。可见示例启动 `todo_host` 后从工具栏打开两个窗口；带草稿关闭主窗口即显示提示。隐藏 smoke 用原生消息覆盖提示窗、父 HWND 禁用、Deny 恢复编辑以及 Allow 后循环退出。
- worker 唤醒接入同一条消息循环：运行时回调在 worker 线程向当前一个存活窗口投递一条 `WM_APP + 1` 消息，宿主处理前多次唤醒合并为一条；窗口增删时唤醒目标切换到仍存活的 HWND。处理消息时调用 `drive_tasks`，逐窗口比较最新呈现快照与该窗口上次构建的快照，只重绘确有变化的窗口。宿主不轮询任务，worker 任务也不接触 runtime；只有宿主的唤醒回调保存窗口句柄并投递消息。关闭窗口后不再接受唤醒：窗口任务迟到的结果按旧 activation 丢弃，应用级结果随宿主释放而不再交付，两者都不能重绘已关闭的窗口。
- `WM_CHAR` 把可打印字符插入当前聚焦的文本输入，一次编辑恰好一次 `on:input`；控制字符忽略，UTF-16 代理项会组合成一个非 BMP 字符。组合中的 `WM_CHAR` 是部分 IME（例如微软拼音）的候选确认路径，走组合提交而不是普通插入；多字符提交由 IME 拆成多个 `WM_CHAR`，宿主按字符逐一编辑。`WM_KEYDOWN` 映射 Backspace/Delete、方向键、Home/End、Shift+方向键（保留 anchor、移动焦点端）、Ctrl+A、Ctrl+Z/Y（撤销/重做）、Ctrl+C/X/V（复制/剪切/粘贴）、Tab/Shift+Tab（运行时焦点顺序）；AltGr 的 Ctrl+Alt 组合不按编辑快捷键处理。Enter 先派发 keydown，未在组合中时提交最近的祖先 form。导航与选择不派发 `on:input`。宿主不保存 caret/selection，导航目标每次从呈现快照计算。
- 宿主不再硬编码 Todo：示例与测试先通过 `zenui_demo::open_todo_window`（可选 `seed`）声明并打开应用窗口，再把它交给 `Host::open`。增删、勾选、过滤与重排全部走运行时模型，隐藏窗口 smoke 用原生鼠标/键盘消息覆盖这些路径。
- `WM_IME_STARTCOMPOSITION` 不交给默认窗口过程：应用按输入框的普通文本样式绘制 preedit，微软拼音若收到默认处理还会再画一份自己的组合窗口，形成两层草稿。`WM_IME_STARTCOMPOSITION` / `WM_IME_COMPOSITION` / `WM_IME_ENDCOMPOSITION` 其余部分映射到运行时组合：`GCS_COMPSTR` 更新 preedit，`GCS_RESULTSTR` 提交并派发一次 `on:input`，空结果或结束消息取消组合。Escape 在组合中取消并恢复文本/caret/selection，焦点丢失、Tab/Shift+Tab 与指针操作同样先取消组合而不写模型。取消时通过 `ImmNotifyIME(NI_COMPOSITIONSTR, CPS_CANCEL)` 同步 OS IME。部分 IME 在 Escape 结束组合时只送达 `VK_PROCESSKEY` 而不发送 `WM_IME_ENDCOMPOSITION`；宿主在本地仍在组合、OS 已无组合串时补一次取消。`WM_IME_CHAR` 不再交给默认窗口过程，避免与结果串重复插入。
- 组合期间每次场景重建都用 preedit 起点处 caret 的物理客户区坐标调用 `ImmSetCompositionWindow` / `ImmSetCandidateWindow`（这两个结构的坐标相对窗口左上角，不是屏幕坐标），锚点夹取进客户区；caret 完全离开视口时把两个锚点移到工作区外，避免把候选窗留在上一次场景的位置。系统组合窗口被抑制，候选窗仍由系统绘制；宿主不绘制自定义候选 UI，也不保存 preedit。微软拼音等 TSF 候选窗在一次组合内缓存屏幕位置：只滚动时宿主已发出新锚点，但候选窗要到下一次 preedit 更新才重排，宿主不因此取消组合或切换 IME 状态。可见证据与边界见 [stage-three 焦点显露验收](../实现/stage-three-焦点显露-验收.md)。
- 布局始终使用逻辑像素，surface 配置使用物理像素。`Host::resize` 按逻辑尺寸调整客户区并立即重绘；`WM_SIZE` 在窗口过程里同步按新客户区重配置 surface 并重绘，`WM_PAINT` 只处理非空更新区域。surface 经 DirectComposition 视觉承载（`Dx12SwapchainKind::DxgiFromVisual`，FIFO）：DWM 合成的是视觉内容，而不是把上一帧位图拉伸到新客户区，因此即使窗口过程来不及出新帧，快速拖动边框时文字也不会先拉宽再回弹；代价是 RenderDoc 无法抓取这类交换链。`Lost` 标记设备丢失；`Validation` 只在当前设备的丢失信号已置位时按丢失处理，否则是 fatal 的 API misuse，不重建。丢失后宿主在设备代际守卫下重建 device、queue、renderer 与每个窗口的 surface，恢复期间不重入，旧设备的迟到回调不会触发第二次重建；重建后按各窗口自己的最新快照重绘。Node ID、焦点、caret、selection、草稿、外观与可见性保留在 Runtime 或宿主中，因此恢复后不变。恢复最多尝试三次；前两次失败通过消息循环重试，不阻塞 UI 线程，三次仍失败时 `run` / `pump` 返回 `HostError::DeviceLost`，其中记录尝试次数、最后一次使用的适配器与失败信息，之后不再创建新设备。`Host::adapter_info()` 报告当前适配器；`fallback` 标识软件回退（WARP），恢复后的回退不会静默发生。契约见 [ADR-0017](../adr/0017-device-loss-recovery.md)；单屏实机尝试记录（未观察到丢失）见[设备丢失实机尝试](../实现/stage-three-设备丢失-验收.md)。
- `Host::read_frame(key)` 用该窗口自己的场景渲染到离屏纹理并读回 BGRA 像素，供 Windows CI 的隐藏窗口 smoke 使用；`HostConfig::hidden` 不调用 `ShowWindow`，但窗口仍创建 surface 并可读回。
- 宿主不持有第二棵 UI 树或编辑器状态；每个窗口仅保存自己的原生句柄、surface 与呈现瞬态。unsafe 只存在于 `zenui-windows`，根 crate 仍 `forbid(unsafe_code)`。
