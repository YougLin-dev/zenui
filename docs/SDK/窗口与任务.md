# 窗口与任务

本页描述目标 SDK 的平台服务边界和窗口生命周期；当前 headless 原型提供可执行的窗口 activation 与任务交付子集，不提供原生窗口。

## Stage-one headless 边界

根包 `zenui` 已经把以下语义做成可运行实现，并用公开行为测试固定：

- `Runtime::open_window(key, factory)` 为目录键创建 activation 和窗口 Owner；每次重开递增 activation，factory 重新执行，旧 activation 的 `WindowCtx` 变为 stale。
- `Runtime::close_window` 释放窗口 UI 和本地资源，取消该 activation 的任务交付，但不销毁共享模型。
- `WindowCtx::task_scope()` 与 `WindowCtx::app_task_scope()` 区分窗口所有权和应用所有权；app 所有权任务可在窗口关闭后继续提交模型。
- worker 只接收 `Send` job 和结果数据；Copy Signal/Memo/Store Field、`WindowCtx`、`TaskScope` 与 `Task` 都不实现 `Send`，UI-only 值不能跨线程捕获。
- worker 结果由 `Runtime::drive_tasks` 在 `Delivery` command turn 中交给 continuation；旧 activation 的结果在交付前被丢弃，continuation 仍受只读作用域和阶段检查约束。
- `Runtime::settle_tasks` 是 headless 驱动的等待入口；它等待 worker 完成后再交付。真实 UI 事件循环应使用非阻塞的 `drive_tasks`，它轮询已经返回的 worker 结果。
- `Runtime::set_wake_callback` 安装 worker 结果就绪时的唤醒回调。回调在 worker 线程执行，必须线程安全且不能借用运行时状态；运行时不合并唤醒——每个已发送结果且未观察到取消的任务唤醒一次，worker panic 不唤醒。
- stage-one 的任务 scope 只有 app 和窗口 activation 两种；单个组件或 `For` 行还不能拥有任务。这样的 continuation 如果写入已卸载分支的 Signal，会在交付 command turn 中被拒绝，而不是静默写入。

以下内容仍只存在于目标设计，不能在 headless 测试中当作已完成：原生窗口展示、隐藏、焦点、菜单/托盘、系统对话框锚点、IME 和 Windows 平台行为。

## 平台对象不参与界面描述

窗口、菜单、托盘、系统对话框属于平台服务。它们不进入 `view!`，也不由某个控件隐式创建与原生生命周期无关的窗口。

应用启动时提交静态窗口目录。目录包含唯一 id、窗口参数和可重复调用的 factory：

```rust
cx.window(
    WindowSpec::new("Todo").primary(),
    Win::Main,
    move |cx| {
        let scope = WindowScope {
            window: cx.context(),
            env: cx.env(),
        };
        Ok(view! {
            <TodoApp
                state={state}
                scope={scope}
                caps={cx.capabilities()}
            />
        })
    },
);
```

这段注册不会打开窗口，也不调用内容 factory。声明失败表示目录未发布；它不意味着可以撤销应用自己执行的随机 I/O 或用户已经看见的宿主副作用。

## 一次打开对应一个 activation

`Win::Main` 是目录中的稳定键，窗口每次真正打开则有独立 activation 和它自己的 Owner。

```text
未打开 -> 打开中(g) -> 可见(g) / 隐藏(g)
                    -> 关闭中(g) -> 未打开
```

这些内部状态带来以下直观行为：

- `primary()` 标记首次显示和默认 reopen 目标；自定义 reopen 走同一条 show 路径。
- 打开的窗口再次 `show()`，聚焦或复用现有实例，不会重复 mount 或创建第二份订阅。
- `hide()` 保留 activation 和本地控件状态，但停止输入、语义动作和呈现；若有待决的关闭确认，这次 hide 按 Deny 结束它，隐藏后不再等待后台 reply。
- `close()` 结束 activation；下一次 `show()` 再执行 factory，创建新 Owner 和新一代本地资源。隐藏的窗口要关闭或重新确认时，先恢复可见再走关闭协议。
- `Retiring` 中的窗口不能被延迟任务提前复用。新的打开请求要么等待退休完成，要么明确返回正在关闭。

目录键与 activation generation 各管一件事。原生 WindowId 或许会被平台复用，不能用它单独判断回调属于哪一次打开。

`WindowCtx` 可以作为 Copy bound handle 携带在事件中；让它复制更方便，不等于保持窗口活着。菜单、任务和延迟 reply 都需要经过有效 activation 的分发检查。

## 关闭确认是一次决定

父窗口可能拒绝关闭并要求确认。系统将这个决定绑定到父窗 activation 和一个 close epoch：

- 同一个 epoch 内，连续点击关闭不会创建多个确认窗。
- “继续编辑”意味着 Deny：关闭确认窗、恢复父窗 input / focus，父窗仍是同一个 activation。
- “放弃修改”意味着 Allow：确认窗与父窗作为一组释放。
- 确认窗的 X 或 Escape 默认是 Deny，不能让确认窗消失后父窗还保持模态禁用。
- 第一个有效 reply 生效。后续迟到的 Allow 不会放行另一代关闭请求。

你可以继续使用 `scope.window.reply(CloseReply::Deny)` 这样的短写法，内部 handle 携带 close epoch 进行判断。不必为了内部去重额外暴露一组长生命周期 token。

关闭策略失败或确认窗构造失败，不能让父窗默认进入 Allow；应恢复可操作状态并报告失败。

如果消失的只是窗口 UI，AppState 可以继续存在。未保存业务状态由独立的 discard / restore policy 处理。

## Hide、Close、Quit 不是一件事

隐藏窗口不会结束应用。关闭窗口默认只处理它的 activation，不天然结束 AppTasks 或共享模型。

退出应用是单独的动作：在某次允许关闭后触发“主窗口关闭即退出”、保持到用户显式退出，或者走平台终止流程，都是应用策略。

收到 session end 后，应用停止新的窗口、dialog 和普通 UI 交付，执行一次有界 flush。它不能等待无限期的 worker，也不应在不可撤销的终止流程中再打开关闭确认。超时、失败和持久化结果具有明确的记录，不能靠一次写 sink 隐藏正在发生的超时。

## UI 事件循环

UI 主事件循环负责处理窗口事件、UI command、布局和呈现。原生回调进入这个循环后，才能修改界面或启动模型操作。worker 经过事件循环桥接唤醒 UI。

菜单命令、鼠标激活、键盘快捷键和辅助动作进入同一个命令路径，各自携带来源与目标身份，防止一次操作被不同路径重复执行。系统拖放、菜单和模态宿主可能产生重入，模型与界面提交始终在已定义的命令边界内完成。

## 对话框的 anchor 与 job owner

系统文件选择器通常需要一个窗口作为宿主锚点，但选择完成后启动的文件导入却不一定属于这个窗口。

```rust
let ticket = import.open(&scope.window)?;
```

这里传入的 `WindowCtx` 是原生展示锚点，不是任务的整个生命周期。Main 关闭后，picker 对应交付可以取消或变为 stale；如果已经选择完文件并且任务是 AppTasks 拥有的导入，模型导入仍可以继续。

用意图决定生命周期：

| 场景 | 适合的 owner |
| --- | --- |
| 行预览、局部动画、窗口临时请求 | 当前 window activation |
| 跨窗口的导入、共享同步、全局错误记录 | application root |
| 只可在进程存活期间运行的 host service | application session |

`task_scope()` 必须来自某个定义清楚的执行位置。窗口 factory 中取得的 scope 不能默认为 app lifetime，系统对话框 anchor 也不能隐式把 job 转到 app root。

## Worker 和 UI 的边界

worker 只取得可 Send 的 job 与结果通道：

```text
选择文件 -> 在 UI 侧创建 ImportJob
         -> worker 读取、解析、生成 PreparedImport
         -> generation-checked UI continuation
         -> 有效的模型事务
```

窗口或 UI 组件的 handle 不应直接变成 worker 的数据解析权限；隐藏窗口暂停呈现，旧 surface 的写入随当前呈现代际结束。

唤醒回调只通知宿主“有事可做”，不交付结果。宿主被唤醒后仍需回到 UI 事件循环调用 `drive_tasks`，在 `Delivery` turn 中执行 continuation；尚未登记 continuation 的结果会保持等待，直到登记为止。回调 panic 会被捕获，不会终止 worker，也不会丢失已发送的结果。关闭与完成竞争时，如果 worker 在关闭前已观察到未取消，唤醒可能发生在关闭之前；该结果仍按旧 activation 丢弃，不会交付到后续 activation。

如果 app import 在窗口关闭后完成，app 级模型可以继续更新，旧窗口 delivery 仍被丢弃。重新打开 Main 后读取的是共享模型的最新状态，不会收到旧窗口或旧 renderer 的延迟回调。

## Host 与渲染的退出顺序

窗口退出先取消输入、IME、语义事件和任务交付，再停止呈现与资源提交，随后释放子窗口 / dialog 和该 activation 的本地状态。应用级 AppState 和 AppTasks 不在其中一并销毁。

device loss、surface recreation 和 renderer fallback 属于渲染恢复，不需要回滚一个无关的模型事务。普通关闭确认协议与平台不可撤销的销毁或 session end 是不同路径，不能强行让两种场景共用一次 Allow 调用。

## Windows 宿主

`zenui-windows` 是第一个平台宿主：一个 HWND 对应一个 activation，关闭窗口时释放该 activation，重开时 window factory 重新执行。宿主用 `windows` crate 直接创建 Win32 窗口，启用 per-monitor v2 DPI awareness，并通过 DX12 surface 呈现 `zenui-render` 的场景；硬件适配器不可用时回退 WARP。

- `Host::open(HostConfig)` 创建窗口、挂载静态 Todo、配置 surface。`HostConfig` 的尺寸是逻辑像素，按系统 DPI 换算为初始物理客户区；`HostConfig::appearance` 设置初始 `Light`/`Dark`，宿主每帧按快照外观选择调色板。应用通过 `WindowCtx::appearance()` / `set_appearance()` 读取和切换外观；外观是已提交状态，切换会失效依赖它的 memo 并重绘，但保留焦点、caret、selection 与编辑状态。surface 只接受 `Bgra8Unorm`；仅提供 sRGB BGRA 的表面会被明确拒绝，因为调色板字节已经按 sRGB 编码。错误通过 `HostError` 返回，不 panic。
- `Host::run` 显示窗口（或保持隐藏）并进入消息循环。窗口过程是输入与绘制的入口：`WM_SIZE` 到达后立即按新客户区重排、重配置 surface 并呈现，使 DWM 不会把上一帧拉伸到新尺寸；`WM_GETDPISCALEDSIZE` 按新旧 DPI 比例换算物理客户区，再按新 DPI 加上非客户区，使 DPI 变化后的逻辑客户区保持不变（最大化/最小化交回默认过程）；该消息不保证每次送达，`WM_DPICHANGED` 仍按系统建议矩形调整并同步重绘，作为兜底；`WM_PAINT` 只处理有实际更新区域的曝光与其它失效。系统的模态拖动/缩放循环直接调用窗口过程，消息循环在此期间收不到消息；因此 `run` / `pump` 在派发期间通过 `GWLP_USERDATA` 暴露裸指针，让窗口过程完成重排与输入处理，指针由 guard 在返回或 panic 展开时清除。`WM_CLOSE` 释放 activation。场景逻辑尺寸来自客户区物理像素除以 DPI scale。HWND 的销毁推迟到 `Window::drop`，保证 surface 存活期间句柄有效。
- 指针瞬态由宿主拥有，不进入 presentation snapshot：`WM_MOUSEMOVE` 经最近一次场景的 `hit_test` 得到最上层启用元素作为 hover，`TrackMouseEvent(TME_LEAVE)` 只注册一次，`WM_MOUSELEAVE` 清除 hover；`Scene::build_with` 通过 `SceneEnv` 读取 hovered、pressed 与键盘模态。每次重建场景前都用最后的指针位置重新命中，节点被过滤、重排或移走后不会残留旧 hover/press。
- 上述瞬态与外观的分工（宿主拥有 hover/press/模态，外观进入快照，场景统一解析样式）见 [ADR-0006](../adr/0006-presentation-transients-and-style-resolution.md)。
- `WM_LBUTTONDOWN` 把物理坐标按 scale 换算成逻辑坐标，再按元素类型处理：文本输入在按下时聚焦并按 `SceneElement::caret_index` 放置 caret；button 与 checkbox 只记录 press 目标并 `SetCapture`，不立即激活；容器与文本清除焦点。`WM_LBUTTONUP` 先取走 press 目标（`ReleaseCapture` 会同步送出 `WM_CAPTURECHANGED`），只有松开仍命中同一个启用节点时才派发 button `click` 或 checkbox `change`；拖出原目标后松开不激活。捕获丢失、焦点丢失与关闭都清除 press。disabled 元素不悬停、不聚焦、不激活，也不改变焦点。派发只依赖 Node ID；宿主不保存 caret、selection 或控件状态。静态元素缺少 handler、不可聚焦或派发中被重挂载时的拒绝是正常交互结果。
- 键盘消息把输入模态切到键盘，指针按下切回指针；`focus-visible:` 只在键盘模态下匹配焦点元素，因此 Tab 聚焦与鼠标聚焦可以有不同的可见焦点样式。
- `Host::pump` 处理所有已排队消息后立即返回，供嵌入外部消息循环或测试驱动单次输入；`Host::scene` 暴露最近一次呈现的场景用于命中与几何查询。
- worker 唤醒接入同一条消息循环：运行时回调在 worker 线程向宿主窗口投递一条 `WM_APP + 1` 消息，宿主处理前多次唤醒合并为一条；处理消息时调用 `drive_tasks`，比较交付前后的呈现快照，只在快照变化时重绘。宿主不轮询任务，worker 任务也不接触 runtime；只有宿主的唤醒回调保存窗口句柄并投递消息。关闭窗口后不再接受唤醒：窗口任务迟到的结果按旧 activation 丢弃，应用级结果随宿主释放而不再交付，两者都不能重绘已关闭的窗口。
- `WM_CHAR` 把可打印字符插入当前聚焦的文本输入，一次编辑恰好一次 `on:input`；控制字符忽略，UTF-16 代理项会组合成一个非 BMP 字符。组合中的 `WM_CHAR` 是部分 IME（例如微软拼音）的候选确认路径，走组合提交而不是普通插入；多字符提交由 IME 拆成多个 `WM_CHAR`，宿主按字符逐一编辑。`WM_KEYDOWN` 映射 Backspace/Delete、方向键、Home/End、Shift+方向键（保留 anchor、移动焦点端）、Ctrl+A、Tab/Shift+Tab（运行时焦点顺序）；Enter 先派发 keydown，未在组合中时提交最近的祖先 form。导航与选择不派发 `on:input`。宿主不保存 caret/selection，导航目标每次从呈现快照计算。
- 宿主挂载 `zenui-demo` 的 `TodoApp`（headless 示例使用同一组件树），`zenui_demo::seed` 预置两条任务；增删、勾选、过滤与重排全部走运行时模型，隐藏窗口 smoke 用原生鼠标/键盘消息覆盖这些路径。
- `WM_IME_STARTCOMPOSITION` 不交给默认窗口过程：应用按输入框的普通文本样式绘制 preedit，微软拼音若收到默认处理还会再画一份自己的组合窗口，形成两层草稿。`WM_IME_STARTCOMPOSITION` / `WM_IME_COMPOSITION` / `WM_IME_ENDCOMPOSITION` 其余部分映射到运行时组合：`GCS_COMPSTR` 更新 preedit，`GCS_RESULTSTR` 提交并派发一次 `on:input`，空结果或结束消息取消组合。Escape 在组合中取消并恢复文本/caret/selection，焦点丢失、Tab/Shift+Tab 与指针操作同样先取消组合而不写模型。取消时通过 `ImmNotifyIME(NI_COMPOSITIONSTR, CPS_CANCEL)` 同步 OS IME。部分 IME 在 Escape 结束组合时只送达 `VK_PROCESSKEY` 而不发送 `WM_IME_ENDCOMPOSITION`；宿主在本地仍在组合、OS 已无组合串时补一次取消。`WM_IME_CHAR` 不再交给默认窗口过程，避免与结果串重复插入。
- 组合期间每次重绘都用 preedit 起点处 caret 的物理客户区坐标调用 `ImmSetCompositionWindow` / `ImmSetCandidateWindow`（这两个结构的坐标相对窗口左上角，不是屏幕坐标）；系统组合窗口被抑制，候选窗仍由系统绘制并锚在 preedit 起点，resize/DPI 重绘后同步更新。宿主不绘制自定义候选 UI，也不保存 preedit。
- 布局始终使用逻辑像素，surface 配置使用物理像素。`Host::resize` 按逻辑尺寸调整客户区并立即重绘；`WM_SIZE` 在窗口过程里同步按新客户区重配置 surface 并重绘，`WM_PAINT` 只处理非空更新区域。surface 经 DirectComposition 视觉承载（`Dx12SwapchainKind::DxgiFromVisual`，FIFO）：DWM 合成的是视觉内容，而不是把上一帧位图拉伸到新客户区，因此即使窗口过程来不及出新帧，快速拖动边框时文字也不会先拉宽再回弹；代价是 RenderDoc 无法抓取这类交换链。`Lost` / `Validation` 会重建 device、surface 与 renderer，然后从最新快照重绘；Node ID、焦点、caret 与 selection 保留在 Runtime 中，因此恢复后不变。
- `Host::read_frame` 用同一场景渲染到离屏纹理并读回 BGRA 像素，供 Windows CI 的隐藏窗口 smoke 使用；`HostConfig::hidden` 不显示窗口。
- 宿主不持有第二棵 UI 树或编辑器状态；unsafe 只存在于 `zenui-windows`，根 crate 仍 `forbid(unsafe_code)`。
