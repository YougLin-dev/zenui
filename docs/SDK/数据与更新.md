# 数据与更新

## 为什么区分状态

界面输入、业务模型、宿主服务和渲染资源变化的方式不同。草稿编辑可以在一个 UI command turn 中即时提交；业务记录可能有失效句柄和事务拒绝；窗口和文件对话框依赖宿主服务；动画帧与滚动帧由 renderer 安排。

ZenUI 把它们分为四类：UI、Model、Host、Render。它们共享明确的数据输入，但不需要共享一种内存模型或错误处理方式。

`Signal`、`Memo` 和 `WriteOp` 是[目标技术架构](../实现/技术架构.md)中的 SDK 数据面。当前 `crates/core` 提供底层探索：可检查的 row identity、RowSet cache、简单 Memo graph 和显式 `Tx` 事务，尚不是已经对齐的最终句柄 API。

## Handle 与 Copy

Copy identity handle 复制的是身份，不是底层数据。`Signal<String>` 可以 Copy，同时不要求 String 自身 Copy；`Memo<String>`、`TodoStore` 和聚合的 `AppState` 同理。

这让 handler、子组件和窗口 factory 可以捕获同一身份，而无需在每一层显式 clone 一份容器。Copy 不延长实体生命周期，也不保证解引用总是有效。

ZenUI 使用安全的 identity handle，而不是把 `Rc`、`Weak` 或裸地址包装成 `Copy`。handle 的访问依赖运行时安装的执行上下文：组件挂载、Memo 计算、事件分发和任务 continuation 分别知道自己所处的 runtime、owner 和 phase。

读取会检查来源、可见性及 generation。事件读取不登记依赖，Memo 和 binding 的读取才登记；同一次计算可以更换不再关心的依赖边。worker 不安装对 UI cell 的读取权限，只接收 Send 工作和返回数据。

## Signal 与 Memo

普通事件里，设置 UI Signal 是即时操作：

```rust
on:input={move |value: String| draft.set(value)}
on:click={move || current.set(Filter::Active)}
```

setter 返回 `()` 的含义是：这个有效的 command turn 已接受修改。它不保证观察者已完成刷新，也不表示 Store 已持久化。

Memo 计算和 binding 不提供这种写入权限。在这些阶段调用 setter 会在修改前被拒绝，而不是写入一部分后再记录错误。

如果普通 `get()` 或 `set()` 在错误运行上下文中调用，那是使用契约错误，不是模型返回的业务错误。框架在调用边界处理这类故障并恢复调度，无需让你给每次输入都加上无意义的 `Result` 分支。需要主动恢复时，可以使用单独的检查接口。

`with` 是只读作用域。即使外层是事件，也不能在 `with` 内调用 setter；内部借用冲突之前就会报告执行错误，不把 `RefCell` 的实现细节当作用户错误协议。

## Store、Field 与行集

Store 的业务对象可以独立于界面消失。因此，UI Signal 有明确值，而 Store Field 可以有失效读取：

```rust
let completed = memo(move || todo.completed.get());
// Memo<Result<bool, FieldError>>

let opacity = memo(move || {
    completed.get().map(|done| if done { 0.55 } else { 1.0 })
});
```

控件和样式 adapter 认识这个结果类型，不把失败翻译为默认值。可选的故障恢复可以保留最后一个已经提交的 frame，但不能把 `Err` 当成重新读取到的 `false` 或 `0`。

`read_once()` 是不同用途的快照读取：

```rust
let title = store.title(id).read_once()?;
```

它不建立持续依赖，适合初次挂载读取 title。相同行的 reorder 不需要重读；行从筛选中消失后重新挂载，允许读取一次。

RowSet 是共享的有序身份投影，只保存行身份，不携带每个消费者各自的标题副本。过滤关注和顺序，字段读取关注字段及所属行的存活性。删除一行时，ZenUI 先根据最新行集撤销该行的监听和订阅，再执行其余字段 binding，使正常删除与失效读取保持不同语义。

## Generation 的用途

句柄身份需要分辨“同一块位置的旧对象”和“现在的新对象”。重开窗口、删除并重建相同业务 key、替换渲染资源时，旧回调不能命中新对象。

业务 ID、row generation、callback registration、window activation、task generation 和 renderer device generation 是独立的维度。有效的 ID 只证明对应维度内的身份，新一代对象具有不可与旧对象混用的代际。

普通的生命周期应由 owner 管理：先取消监听、订阅和结果交付，再释放子 owner 与对应控件状态。复制一个 handle 不会中断这条释放路径。被卸载分支的旧事件不带入新的 interface generation。

## 写入、标脏与统一刷新

一次合法交互使用独立、可控的 command turn：

1. 检查事件和 callback registration 是否活着。
2. 在对应执行上下文中调用 handler 一次。
3. 完成这次允许的 UI 写入和模型操作。
4. 恢复前一层执行上下文。
5. 计算稳定的派生值与控件 patch，再统一发布。

setter 和模型事务不负责在任意 Rust 表达式中间同步重入并刷新所有观察者。合法的嵌套读取会恢复环境和依赖归属；worker completion 经过检查后成为新的 UI 交付，不沿用旧窗口上下文。

如果写入来自非法 phase，应在变更与用户后续动作之前停止它。仅在事后把错误送进队列、但让 handler 正常继续，不足以约束副作用。

## WriteOp 与模型事务

`WriteOp<T>` 描述尚未执行的模型操作。创建它是惰性的：不会因为调用构造函数而修改 Store、保留行号或发起 I/O。

在不同入口中：

- handler 尾值返回 `WriteOp`，adapter 在当前 command turn 内用一个模型事务执行它；
- `Transaction::new().write(op).finish()` 显式组成模型事务；
- 未提交的 op 不会被 `Drop` 自动执行；
- Memo、binding、layout 等阶段不能执行模型事务。

`Transaction::new()` 是独立的模型提交边界，提交内容是一个模型内的暂存和协调操作。UI、窗口、GPU 与文件操作各自具有独立的提交与结果。

## Add 为什么可以提交后清草稿

新增 Todo 与清空输入框来自不同领域。ZenUI 不把 UI reset 强行加入业务事务：

```rust
let add = move || -> Result<(), AppError> {
    let title = draft.with(|text| text.trim().to_owned());
    if title.is_empty() {
        return Ok(());
    }

    Transaction::new()
        .write(todos.insert(title))
        .finish()?;

    draft.set(String::new());
    Ok(())
};
```

这里先有同步内存模型提交，再修改草稿。两者在同一 command turn、没有中途输入交错的条件下完成，随后统一 flush。这种产品语义很明确：模型成功后才清理草稿，不声称它是跨 Store 和 UI 的原子事务。

若清空动作要等异步结果，需要捕获 draft revision，只有草稿仍然和提交时一致才清理，避免覆盖后续输入。

## 异步与持久化

异步 job 的输入输出必须能安全跨线程传递：从 UI 侧创建 job，worker 读取文件、解析或生成 prepared result，再交给 generation-checked continuation 完成 Store 事务。

worker 不能直接捕获 UI Signal、Memo、WindowScope 或 renderer attachment 并写它们。哪个任务 scope 拥有工作，决定它能否在窗口关闭后继续；哪个 activation 拥有交付，决定结果是否还有可见接收者。

保存完成、模型提交完成、worker 完成和 UI 交付是不同事实。不确定的持久化状态不能被 UI target gone 改写为失败。需要重试时，应使用能识别重复提交的命令身份，而不是盲目再次执行整个效果。

## 错误报告

错误通道负责报告和展示，它不授予写入权限、不能决定是否回滚，也不能代表任务已经被取消。

使用中的错误分为：

- 业务操作被拒绝；
- 宿主或持久化操作失败；
- framework 调用契约错误；
- 目标已消失或 superseded delivery。

错误展示与根诊断分离，由当前 command turn 统一交付。正常行删除、过期结果交付和真正的用户操作失败分别归类。
