# 从空目录开始

本页说明如何在仓库之外的目录创建可运行的 ZenUI 应用：复制模板，或把 `zenui` 与 `zenui-windows` 声明为 git 依赖。两种路线都以 Windows 10/11 x64 上的可见窗口为目标。

ZenUI 仍在 1.0 之前，根包与模板都设置 `publish = false`，没有发布到 crates.io。依赖只能来自仓库路径或 git；API 和模板会随仓库变化，本页不是稳定版本承诺。Linux 与 macOS 目前只有 headless 部分，没有原生宿主。

仓库中由 ZenUI 项目编写的代码与文档以及模板以 `MIT OR Apache-2.0` 双重许可发布；第三方内容与资源保留各自许可。许可全文见 [LICENSE-MIT](../../LICENSE-MIT) 与 [LICENSE-APACHE](../../LICENSE-APACHE)。

## 环境

| 项 | 要求 |
| --- | --- |
| 操作系统 | Windows 10 或 11，x64 |
| Rust | 用 [rustup](https://rustup.rs/) 安装；模板的 `rust-toolchain.toml` 固定工具链，第一次执行 Cargo 命令时自动安装 |
| C++ 构建工具 | Visual Studio Build Tools 的“使用 C++ 的桌面开发”工作负载，包含 MSVC 链接器与 Windows SDK；`rustup` 使用 `x86_64-pc-windows-msvc` 工具链 |
| 图形 | 支持 DX12 的 GPU 与驱动。没有可用硬件适配器时宿主请求 WARP 软件适配器（`GpuAdapterInfo.fallback` 为 `true`），性能与部分呈现能力受限；CI 的隐藏宿主 smoke 只做隐藏窗口读回，宿主在没有硬件适配器时走这条回退路径 |
| 磁盘 | 从零的 debug 构建约 2.2 GB，debug 与 release 合计约 3.5 GB；建议预留 5 GB |
| 会话 | 打开可见窗口需要交互式桌面会话；Windows 服务或没有桌面的 CI 会话只能使用隐藏宿主 |

## 路线 A：复制模板到仓库外

模板位于仓库的 `templates/minimal-app`，是独立 workspace，拥有自己的 `Cargo.lock` 与 `rust-toolchain.toml`。复制到仓库外后，只需把两个 path 依赖改到你的 checkout。

1. 克隆仓库，记下 checkout 的绝对路径：

   ```sh
   git clone https://github.com/ZenUIOrg/zenui.git /path/to/zenui
   ```

2. 把模板复制为一个新的应用目录。目标目录必须不存在，`cp -R` 会创建它：

   ```sh
   cp -R /path/to/zenui/templates/minimal-app /path/to/hello-zenui
   cd /path/to/hello-zenui
   ```

   PowerShell 中对应的命令是 `Copy-Item -Recurse`，同样不要预先创建目标目录。如果 checkout 里的模板已经构建过，复制后删除副本的 `target/`，不要带入旧缓存。

3. 编辑 `Cargo.toml`，把两行 path 依赖指向 checkout。模板在仓库内时它们是相对 `../..` 的路径；复制后这个相对路径已经不再指向仓库：

   ```toml
   [dependencies]
   zenui = { path = "/path/to/zenui" }
   zenui-windows = { path = "/path/to/zenui/crates/windows" }
   ```

   Windows 路径使用正斜杠（`E:/code/zenui`），或在 TOML 字符串中转义反斜杠。

4. 构建并运行：

   ```sh
   cargo run --locked
   ```

   窗口标题为 `ZenUI Starter`，`Increment` 按钮增加 `Count`，关闭窗口退出。模板保留 `Cargo.lock`，改写 path 依赖后 `--locked` 仍然可用。

这正是 CI 的 `Template copy-out (Linux)` 步骤执行的检查：把模板复制到 checkout 之外，改写两个 path 依赖，再运行 `cargo test --workspace --locked`。Linux 上只运行跨平台测试；Windows 宿主测试仍由 Windows leg 在仓库内执行。CI 只构建和测试，不显示窗口。

## 路线 B：新包 + git 依赖

仓库没有发布到 crates.io，但 Cargo 可以直接从 git 构建 `zenui` 与 `zenui-windows`。依赖必须指向仓库中存在的修订：commit SHA、branch 或 tag 都可以，Cargo 会把 branch 解析成当时的提交；`rev = "HEAD"` 不是有效的 revspec。

1. 新建包目录，并从 checkout 复制模板源码与工具链文件：

   ```sh
   mkdir -p /path/to/hello-zenui/src
   cd /path/to/hello-zenui
   cp /path/to/zenui/templates/minimal-app/src/*.rs src/
   cp /path/to/zenui/templates/minimal-app/rust-toolchain.toml .
   ```

   包名保持 `minimal-app`：模板入口按这个 crate 名调用 `open_starter_window`。不要复制模板的 `Cargo.lock`，首次构建会为 git 依赖生成新的 lock。

2. 写 `Cargo.toml`。本地 checkout 使用 `file://` URL，`rev` 取 `git -C /path/to/zenui rev-parse HEAD` 的输出：

   ```toml
   [package]
   name = "minimal-app"
   version = "0.1.0"
   edition = "2024"
   publish = false

   [dependencies]
   zenui = { git = "file:///path/to/zenui", rev = "<commit>" }
   zenui-windows = { git = "file:///path/to/zenui", rev = "<commit>" }

   [profile.dev.package."*"]
   opt-level = 3

   [profile.dev.package.zenui-render]
   opt-level = 2
   ```

   Windows 的本地 URL 写成 `file:///E:/code/zenui`。也可以改用远程仓库：

   ```toml
   zenui = { git = "https://github.com/ZenUIOrg/zenui.git", rev = "<commit>" }
   zenui-windows = { git = "https://github.com/ZenUIOrg/zenui.git", rev = "<commit>" }
   ```

   `branch = "main"` 跟随分支移动；`rev` 与 `tag` 适合可复现构建。`rev = "HEAD"` 会被 Cargo 拒绝：

   ```text
   revspec 'HEAD' not found; class=Reference (4); code=NotFound (-3)
   ```

   两段 profile 设置与模板一致，只优化依赖，保留应用 crate 的增量编译速度；可以省略，但 debug 下的布局与绘制会明显变慢。

3. 构建并运行：

   ```sh
   cargo run
   ```

   如果这个目录位于另一个 Rust workspace 内，在清单中加入空的 `[workspace]` 表，让它成为独立 workspace。

CI 的 `Git dependency resolution (Linux)` 步骤在 checkout 上创建临时 branch 与 tag，分别用 `rev=<SHA>`、`branch=...`、`tag=...` 构建 scratch app；同一个步骤还断言 `rev = "HEAD"` 以 `revspec 'HEAD' not found` 失败。

## 发布构建

release 构建产出单个可双击运行的 exe：

```sh
cargo build --manifest-path templates/minimal-app/Cargo.toml --release --locked
```

模板在仓库内且未设置 `CARGO_TARGET_DIR` 时，产物是 `templates/minimal-app/target/release/minimal-app.exe`；复制到仓库外的应用是 `<应用目录>/target/release/minimal-app.exe`。设置了 `CARGO_TARGET_DIR` 时，路径是 `<CARGO_TARGET_DIR>/release/minimal-app.exe`；CI 的 Windows leg 使用共享 target，并在构建后断言该文件存在且子系统为 GUI。CI 只验证这个共享 target 变体；默认 `target/` 路径由本地 release 记录支持。

release 入口按 `debug_assertions` 切换子系统：release 使用 Windows GUI 子系统，双击只显示窗口，不附带控制台；debug 保留控制台便于诊断。PE 头的 subsystem 值为 2 表示 GUI，3 表示控制台。

exe 是可移植的单文件：复制到另一个目录后双击即可运行，不读取相邻的 asset、字体或工作目录配置。模板不包含 asset 或字体文件，文本使用系统字体。`target/release` 中的 PDB 与中间产物只是构建输出，不作为分发内容；分发只复制 exe 与许可证文本。运行环境仍需：

- **MSVC C 运行时：** 当前 release 产物导入 `VCRUNTIME140.dll` 与 6 个 `api-ms-win-crt-*` API set；目标机器需要 Microsoft Visual C++ 2015–2022 Redistributable（x64），UCRT 的 API set 由 Windows 10/11 提供。产物不导入 `MSVCP140.dll`。
- **图形：** 与[环境](#环境)一节相同，需要支持 DX12 的适配器；没有硬件适配器时宿主尝试 WARP 软件适配器。
- **未签名：** exe 没有代码签名；从网络或另一台机器复制后首次运行可能触发 SmartScreen「Windows 已保护你的电脑」，需要「更多信息」→「仍要运行」。

模板只产出这个 exe，不提供 installer、自定义 icon/version resource、代码签名或 auto-update，也不把这些能力当作发布承诺。分发 exe 时请随附仓库根目录的 [LICENSE-MIT](../../LICENSE-MIT) 与 [LICENSE-APACHE](../../LICENSE-APACHE)。

发布构建的可见运行（复制 exe 到另一个目录、无控制台、UIA 计数）记录在 [stage-three 发布打包验收](../实现/stage-three-发布打包-验收.md)；CI 对 release 只做构建、exe 路径与子系统断言（另有 LICENSE 校验步骤）。

## 第一次构建的时间与磁盘

以下是在一台 24 逻辑核 Windows 机器上构建模板与 git 依赖的测量，不是 CI 承诺：

| 项目 | 测量 |
| --- | --- |
| `cargo test --workspace --locked`（独立 target） | 约 145 秒 |
| 仅 debug 的 target | 约 2.2 GB |
| 追加 `cargo build --release --locked` | 约 65 秒 |
| debug 与 release 的 target 合计 | 约 3.5 GB |
| git 依赖的首次构建（本机） | 约 3 分钟，含检出与编译仓库源码 |

增量构建通常只需数秒到数十秒。CI 的 4 vCPU runner 明显更慢：`windows-test` 预留 40 分钟，Linux/macOS 的 `workspace` job 预留 60 分钟。默认 target 位于应用目录的 `target/`；需要共享编译缓存时设置 `CARGO_TARGET_DIR`。

## 验证边界

- **CI：** `workspace` job 的 `Template copy-out (Linux)` 与 `Git dependency resolution (Linux)` 步骤在 Ubuntu 上验证复制、path 改写、git 修订解析与 `HEAD` 拒绝。Windows 的模板检查拆在独立的 `windows-*` job：`windows-template-lint` 与 `windows-template-release` 在 Blacksmith 上做 format、clippy 与 release 构建，`windows-template-test` 留在 GitHub 托管的 `windows-latest` 上运行测试。release 步骤断言 `<CARGO_TARGET_DIR>/release/minimal-app.exe` 存在且 subsystem 为 GUI；其中隐藏宿主 smoke 只做隐藏窗口读回，宿主在没有硬件适配器时回退 WARP。CI 不运行可见窗口。
- **可见运行：** 在 Windows 11、单屏 150% 下，从仓库外的复制目录构建并打开 `ZenUI Starter`，用 UI Automation 按下 `Increment` 并读回计数。记录、截图与边界见 [stage-three 空目录启动验收](../实现/stage-three-空目录启动-验收.md)。
- **发布可见运行：** release exe 复制到另一个目录后启动，窗口无控制台，UIA 计数正常。记录、截图与边界见 [stage-three 发布打包验收](../实现/stage-three-发布打包-验收.md)。
- **路线 B 的源码：** 用模板的 `src/` 与 git 依赖在本机构建通过；可见截图来自路线 A 的同一份源码，不把两条路线的构建证据混为可见窗口证据。

## 故障排查

| 现象 | 处理 |
| --- | --- |
| `link.exe not found` 或链接器错误 | 安装 Visual Studio Build Tools 的 C++ 桌面工作负载与 Windows SDK，确认 rustup 使用 `x86_64-pc-windows-msvc` |
| 创建适配器失败或提示 `NoAdapter` | 更新显卡驱动；虚拟机或 RDP 会话可能没有兼容的硬件适配器，宿主会尝试 WARP；仍失败时改用本地交互式桌面会话 |
| `revspec 'HEAD' not found` | 用 `git rev-parse HEAD` 的完整 SHA，或改用存在的 `branch`/`tag` |
| `failed to load source for dependency` | 检查 `file://` URL 是否指向仓库根，Windows 本地路径需要三个斜杠（`file:///E:/...`） |
| `no matching package named zenui found` | `zenui` 未发布到 crates.io，依赖只能来自 path 或 git |
| 复制后仍然引用旧路径 | 检查 `Cargo.toml` 的两个 path 依赖是否已改为 checkout 的绝对路径 |
| 缺少 `VCRUNTIME140.dll` | 安装 Microsoft Visual C++ 2015–2022 Redistributable（x64）后重试 |
| SmartScreen 阻止首次运行 | exe 未签名；选择「更多信息」→「仍要运行」。模板不提供代码签名 |
