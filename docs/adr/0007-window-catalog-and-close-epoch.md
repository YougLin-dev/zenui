# Window activations own UI state; the runtime owns close epochs

A window key names a catalog entry, not a live tree. `Runtime::declare_windows` publishes the static `WindowSpec` catalog (key, title, logical size, primary flag, `ClosePolicy` and `WindowRole`); declaration mounts nothing, and every open runs the factory again. Each activation owns its UI tree, focus, caret/selection, IME state and presentation snapshot; the Host maintains the matching HWND, `Scene` and `Surface` for that activation. A closed activation releases all of them and is never revived; reopening the same key creates a new activation generation, and every `WindowCtx` or `CloseRequest` from the old generation is rejected. The application owner keeps the shared Store, Signals, Memos, appearance and app-scoped tasks, so several activations observe one model without sharing edit state. The Host routes native input by HWND and mirrors runtime visibility, focus and enabled state; it does not keep a second tree or editor.

Close is a runtime decision. `ClosePolicy::Confirm` creates at most one epoch per parent activation, records the parent's focused node, suspends parent input, and invokes a handler registered during the factory with a one-shot, epoch-bound `CloseRequest`. The catalog declares the confirmation window with `CloseConfirmation { parent }`; that window reads the pending request through `close_request()` and replies Allow or Deny. Allow releases the parent and confirmation as a group; Deny releases only the confirmation and restores the parent's input, focus and caret. X, Escape or a close request on the pending confirmation means Deny; the first valid reply wins, later and cross-epoch handles are rejected, and a missing or panicking handler, or one that never shows the declared confirmation window, leaves the parent open with an explicit error. The Host's `WM_CLOSE` is only a driver: it calls the same runtime request path, disables the suspended parent with `EnableWindow`, and settles replies after input or task delivery.

## Considered Options

- **One retained tree with per-window roots, or per-window state in the Host**: the Host would become a second UI authority, and window lifetime could not be tested without a native message loop. Rejected; one runtime owns trees, focus and close decisions.
- **Host-owned or framework-drawn confirmation UI**: the framework cannot know the application's copy and actions, and an implicit platform window would bypass the catalog and the headless close path. Rejected; the application declares its own confirmation window.
- **Dynamic window creation from handlers instead of a static catalog**: titles, sizes and the confirmation binding would move into callbacks, while declaration-time validation (duplicate keys, primary count, invalid confirmation parents) would disappear. Rejected for this milestone; later dynamic creation can extend the same identity rules.
- **A second policy such as `ConfirmIfDirty`, or one global pending-close flag**: a handler can allow synchronously when no prompt is needed, and an epoch-bound handle gives first-reply, duplicate-reply and stale-reply semantics without global mutable state. Rejected.
- **Binding an existing confirmation window at runtime**: static `confirmation_for(parent)` lets declaration reject a missing parent, a non-`Confirm` parent, a self-parent, duplicate confirmations and nested confirmation windows. Rejected runtime binding.
- **Treating hide as close, or reopening the same activation**: hide must preserve local edit state and close must release it. Two distinct transitions keep every reopen a new activation and make stale delivery impossible. Rejected merging them.

## Consequences

`WindowCtx` and `CloseRequest` are Copy identities and do not extend lifetime; every operation validates activation and epoch. Snapshots and scenes are per window while appearance and model data are shared. The Host synchronizes after every message and task delivery, and the loop exits when no window remains live. Hidden and WARP tests cover routing and the close protocol but are partial evidence; visible window checks are required (ADR-0005), and #63's cross-monitor DPI and real device-loss gaps remain open. The stage-three milestone records auto-driven visible evidence at 100% and 150% and does not claim the manual items of ADR-0005; see [stage-three multi-window acceptance](../实现/stage-three-多窗口-验收.md).
