# ZenUI 写作

面向开发者解释 ZenUI 如何工作，或 API 在边界上保证什么。
按任务交付文档、润色后的文本、变更 diff 或附有原文的审查意见。

## 起始检查

1. 从当前代码、测试和读者动作确认事实；历史文本提供线索，不能替代对目标规则的论证。
2. 区分目标模型、当前交付和进度记录：目标说明陈述预期接口，实现进度由现有路线或验收记录承载；全文统一交代范围，不按段混用已实现语气。
3. 找到同主题已有说明与相邻模块。移动归属、保留核心规则或归并重复内容；不为同一概念另建入口副本。

存在与当前代码、测试或文档的冲突时，指出具体事实与编辑方案；由任务约定确定要改的目标或实现，不能用旧文档否决已确认的目标。

## 文档

使用中文，专业、克制、具体。教程以“你”称呼读者；架构以 ZenUI、接口和组件作主语。直接描述主体、条件、动作和结果。

- 将内容放入现有 `产品`、`SDK`、`实现` 分类；移动到合适归属优于增加平行导语与重复导航。
- 同一段保持一致的时间、层级和视角。术语采用项目当前定义，不引入未定义缩写。
- 开头让读者确定文档讲什么；结尾留下可操作的行为或可验证的接口。合并重复目标、边界和正文中的反复宣言。
- 只呈现改变选择的机制与约束。省略作者心路、评审身份、汇报口吻和自我辩护，包括“我们必须……”、“为了短期……不能……”的反思段。
- 示例标明目标 SDK、现有 API 或伪代码的范围。编译、测试和真机操作是能力的证据；target 文档、shape 示例和 headless 测试不能转换为 GUI、IME、UIA 或 GPU 已交付的承诺。

内部小组件保留代码里可以检索的名称；commit、PR、issue、ADR 或调研对象不应替代接口说明。必须追溯决策时，先写清局部机制，再附对应参考。

## Rust 注释

公共 API 的 `///`、`//!` 描述调用契约；普通 `//` 解释局部实现的 why 或不变式。先读它所属函数和相邻调用，再提炼独立成立的描述。

`#[doc]` 属性与 `///` 产生的文档承担相同契约要求；内部注释不承担外部阅读入口。

- 命名、类型、签名和断言已经表达的内容直接留在代码中；不以注释复述函数名或逐行翻译表达式。
- 注释紧跟所解释的代码。删除无法经局部事实支持的目的、历史和设计感想。
- 生命周期、跨阶段时序、缓存键、失效、所有权及非显然外部约束，需要写出读者无法从代码直接得到的那条 why。
- 外部引用不承担行为解释：先在本处完整陈述不变式，必要时再附一个精确定位到相关行为的理由或出处标签。
- 废除条件、成立前提或反直觉做法说明触发条件与替换依据，不使用空泛的临时方案标记；用实际项目任务表示时间关系。

新写的文档和 Rust 注释使用中文。注释格式遵守相邻文件的 Rustdoc 约定；不把整本文档按同一短语模板重写。

修改与注释相关的调用条件、生命周期、跨阶段提交、失效或安全边界时，检查同一函数的每个相关分支及必要调用方，并同步已有契约文字。

## 示例

以下示例展示文本处理方式，不是待运行的完整 API。

公共 API 给出可解析的行为与前置条件：

```rust
/// 提交此次激活对应的已暂存窗口更新。
/// 已关闭的激活返回 `ActivationError::Closed`；宿主已发生的操作不会回滚。
fn commit(&mut self, activation: Activation) -> Result<(), ActivationError>;
```

局部注释只写代码不能直接读出的时序：

```rust
// 后序栈再次访问父节点时，所有已登记子节点都已释放；
// 父级 cleanup 此时仍可读取其状态。
while let Some(owner) = pending.pop() {
    // 展开与收尾沿显式栈推进。
}
```

## 收尾

创建或修改后，逐项验证本次改动承载的完整结果：

- 回归目标：确认目标模型、交付断言处于各自正确的时态和范围；支持的声明有代码、测试或实际运行对应。
- 回归读者：一个目标文档有清楚入口与分类，同一规则只有一个权威归属；没有新增组织、内心独白或既有含义的重复陈述。
- 回归可用：文档示例经真实编译或说明目标/伪代码状态；代码注释解释的分支和条件均在当前实现存在，无需外部历史即可理解。

只读审查按文件和行号给出具体问题、原因与替换建议；不执行全文风格化改写。只改措辞时不自行声称编译或系统行为得到验证。
